# GoodVibes 3.3.0

This release changes who decides what the agent may do, and how quickly it
gets there. Facts the program already holds are settled in code with no model
request and no question: a read, a search, an edit inside the workspace and a
command an existing rule covers start at once. You are asked only what is
yours to decide, once, and the answer is remembered. Everything in between is
a judgment call for Jev, the decision model, with a deadline and a fallback so
nothing hangs. One setting, `permissions.mode`, chooses how much you are asked;
one setting, `judgment.policy`, chooses whether a decision model is used and
what happens when it fails.

The release also makes the product much faster on the paths you use most
(see [Speed](#speed)), closes a long list of security gaps (see
[Security](#security)), and finishes features that were half built: the owner
inbox, autonomous purchases within your limits, per-tool MCP rules, parallel
tool calls and the shared work plan. A few things the owner decided to retire
are gone (see [Removed](#removed)), and data from before this release that the
product stopped reading is not carried over (see [Upgrade notes](#upgrade-notes)).

The 3.3.0 tree contains 2,094 commits since 3.2.0.

## Who decides: permission modes

`permissions.mode` has four values. The default is `jev-decides`.

| Mode | What happens |
| --- | --- |
| `ask-me` | Jev reads each judgment call's risk. Low-stakes calls run; high-stakes calls and owner-only items ask you. |
| `jev-decides` | Jev decides judgment calls; owner-only items ask you. With no working decision model it behaves as `ask-me`. |
| `just-vibes` | Nothing interrupts you. Jev decides judgment calls when a decision model works; anything that needs you is held and listed at the end of the run, where `/held` approves or sets it aside. |
| `yolo` | Calls run without approval prompts. Authentication, workspace containment, secret storage and spending limits still apply. |

`plan` remains a separate read-only posture.

- **Owner-only items.** A closed list always comes to you, in every mode except
  `yolo`, and Jev never answers for you: spending over a limit you set, a
  deletion nothing can bring back, sending as you to a new recipient, sending
  content derived from untrusted text read in the same turn, granting access
  (pairing, MCP trust, channel allowlists, hooks), loosening a security,
  judgment or payment setting, and changing what a contract requires. A
  command that might wipe the machine or your data wholesale is asked for that
  one call; nothing is offered to remember. You are asked once and the answer
  is remembered where remembering is safe.
- **The default and calibration.** While `jev-decides` is only the default
  (you have not chosen a mode), Jev decides for you only on a decision model
  whose gate decisions were measured and passed: the release ships a passing
  calibration record for `jev-latest` (answered by `jev-1.14.0`), covering all
  49 decisions the permission gate asks. On any other decision model the
  default asks you, as `ask-me` does, until you choose `jev-decides` yourself.
- **Shift+Tab** changes the mode of the current session only; the saved
  default stays in `/permissions` and Settings. Entering `yolo` asks once, with
  No preselected. The key is the rebindable `cycle-permission-mode`.
- **`--just-vibes` and `--yolo`** pick a mode for one launch of `goodvibes`
  without changing settings.
- **`/decisions`** lists what Jev decided for you at the permission gate, in
  both terminal apps and the web UI. For each one you can undo it (files the
  call changed are restored when its tool recorded them), turn it into a
  standing rule (never, always, or always ask me), or keep it.
- **`/held`** lists what `just-vibes` held instead of asking, and approves or
  sets aside one item or all of them. A hosted `just-vibes` session puts its
  held calls in the owner inbox.
- **A call routed to you is asked or held, never approved in your name.** A
  lower layer (the terminal app's exec sandbox) settles an ask only when the
  gate marked it containable, and that answer is recorded as the sandbox's,
  not yours.
- **Every tool result that is not a plain success carries one decision
  object** with its state, who decided, the reason and the next step, so the
  agent can tell a refusal from a held call or an error.

## Decision model policy

`judgment.policy` has three values. The stored value names are new.

| Value | When the set decision model fails |
| --- | --- |
| `Hybrid` (default) | The operation continues without it: each decision takes its stated fallback, and you are told once, naming the model, what failed and the next step, and once again when it answers. |
| `Decision Model Only` | Work that needs the model stops and reports the model, what failed and the next step. |
| `No Decision Model` | No decision-model request is made. |

- **With no decision model set** (no `judgment.endpoint`, `judgment.model`,
  `judgment.fallbacks`, credential choice, `TYPESAFE_API_KEY`,
  `TYPESAFE_BASE_URL` or `TYPESAFE_DEFAULT_MODEL`), every policy runs without
  one: nothing is asked, nothing waits, nothing reports an error. A fresh
  install works before any decision model is configured.
- **You can always tell when no decision model is in use.** The conversation
  says so once; `goodvibes status`, `goodvibes doctor` and
  `goodvibes-agent status` print a "Decision model" section; a headless run
  prints the line on stderr and adds `diagnostics.decisionModel` to its JSON
  result without changing the exit code; the web UI shows it in a bar under
  the header.
- **Deadlines.** A decision that you or a tool call wait on gets one request
  bounded by `judgment.decisionDeadlineMs` (default 1500 ms) and takes its
  fallback when the model is off, slow, unavailable or unsure. A decision
  target that misses its deadline three times in a row is skipped for a
  minute. A target that refuses the connection is not asked twice.
- **Outages are reported as outages.** A rejected key is reported as rejected
  with its status; "rate limited" is said only for HTTP 429.
- **Features that only work with a decision model** (autonomous contract
  execution, Home Graph generated pages, semantic knowledge answers and
  repair, checkout interpretation, gift planning, the Decision Router's
  categorization and a few others) say "No decision model is in use, so this
  part is not available" instead of failing. Over the daemon API they answer
  409 `DECISION_MODELS_DISABLED` with what to do instead of 500.

How much you are asked under each combination is described in the
[decision model policy guide](https://github.com/mgd34msu/goodvibes/blob/v3.3.0/docs/decision-model-policy.md#how-much-you-are-asked).

## What changed in behaviour

### Workspace trust and repository content

- **A repository's `hooks.json` and MCP files run nothing until you trust the
  workspace.** In both terminal apps, a `hooks.json` inside an untrusted
  workspace is not loaded, and the MCP servers its `.mcp/mcp.json` or
  `.goodvibes/mcp.json` name do not start or replace yours. An undecided
  workspace counts as untrusted; the app says so once at start, and trusting
  the workspace turns them on at once. Your own hooks and MCP files are not
  affected. The Agent gains `/trust workspace trusted|restricted`.
- **A project can no longer mark itself trusted.** Trust decisions live in
  your own workspace register, keyed by the directory's real path; a
  `trust.json` inside a project is reported, not honoured. An undecided
  workspace raises one question that stays open until answered; reads run
  meanwhile, and after ten minutes unanswered, later writes, commands and
  delegation are refused at once with the next step instead of waiting again.
- **A project settings file sets only display, behaviour, contract, worktree
  and stricter permission settings.** It can no longer loosen your safety
  settings or run commands.
- **A project's `services.json` adds only services whose credentials are keys
  in your secret store**; command references and sign-in blocks come only from
  your own file. A project's secret store is read only at the project root, and
  a key in it is used once you confirm it with `/secrets trust`.

### Purchases

- **Limits default to 0, and the first time a purchase meets one you are
  offered the chance to set it.** `payments.budget.dailyItem` and
  `payments.budget.perPurchaseCeiling` start at 0, so by default every purchase
  asks you. The first time a purchase meets one of them at 0, the owner inbox
  asks for the amount and the daemon writes your answer to the setting. You are
  asked once per limit; 0 or no keeps it unset.
- **Inside your limits the agent buys without asking.** It opens a veto window
  (`payments.windows.vetoMinutes`, default 10): the notice is in your owner
  inbox and on `payments.notifyChannels`, one word (stop) cancels it, and
  silence lets it go ahead.
- **Outside your limits it stops and says which limit and by how much**, for
  example "comes to USD 30.00 and is over the per-purchase ceiling of USD 20.00
  by USD 10.00", and opens an approval window
  (`payments.windows.approvalMinutes`, default 60) where silence denies.
- **With no decision model in use**, a checkout that no model read is put to
  you as an explicit approval that lists what was not checked; silence never
  buys.
- **Pre-approval of every purchase is optional and off by default**
  (`payments.confirmEveryPurchase`). An approval given in advance from the web
  UI's Purchases panel or `/payments approve` still answers its window.
- **Limits apply on every path:** the per-purchase ceiling covers the full
  total, a card's declared issuer cap and `payments.defaultCardId` apply, and
  order buttons clicked outside the purchase flow are refused.
- **The order is submitted once.** An ambiguous click is reported as submitted
  with its outcome unknown and is never retried; the budget stays reserved
  until the order is confirmed or reconciled. A shop's confirmation mail
  settles a purchase whose page showed no confirmation.
- **A purchase waiting on you survives a daemon restart**, and can be answered
  from any app, from the owner inbox, or on channels other than Telegram.
- **Scheduled purchases** can buy what you authorised in advance:
  `/payments standing add` sets the item, shops, per-purchase and per-period
  maximums and an optional last day.
- **The Agent can start and cancel purchases again**, and may change payment
  settings when you ask it to in the turn. Card details, credential
  destinations and secret references stay yours to set.
- **eBay purchases** read the listing: auctions and Best Offer are refused, and
  the two seller thresholds decide whether a Buy It Now purchase proceeds on
  silence or asks first.

### One owner inbox

- **One owner inbox per home** (`~/.goodvibes/shared/owner-inbox.sqlite`) that
  the daemon, both terminal apps and every running copy read and answer at
  once. A question asked in one app shows in all of them; an answer given
  anywhere reaches the asker on its next model request, with no restart.
- **The `query` tool is a real feature:** an agent leaves you a question and
  carries on. You answer with `/questions` (alias `/inbox`) in either terminal
  app, in the web UI's Work page, or from a phone push when push is enabled.
- **Contract questions wait in the owner inbox**: a failed unit's retry or
  cancel question, the "accept the unchecked result" question and any other
  question a contract asks. An answer given in the inbox is handed to the
  contract exactly as `contracts.reply` hands it; a reply given elsewhere
  withdraws the item.
- **A message from a sender not on a channel's allowlist** is held as one inbox
  item per sender instead of being dropped; accepting adds the sender to the
  allowlist, declining is remembered.
- **An inbox answer typed in a terminal app is recorded as answered there**,
  not as answered from the web.

### Mail

- **Mail inbox rows carry a screening field.** Each row says `screened`, or
  `not-screened` with the reason (no screening route, no decision model in
  use, or a screening failover). The subject stays exactly as received. The
  TUI's `/mail list` tags such rows `[not screened]`, the Agent's unified
  inbox says so, and the web UI mail view shows a "Not screened" chip.
- **Mail reaches the mail inbox without a screening route.** Without screening
  consent or credentials, the email inbox is built unscreened instead of being
  unavailable; a plaintext mailbox is accepted on a loopback host only.
- **Mail no longer stalls behind one message it cannot deliver**; a message is
  handled once even when a provider sends it again; mail that arrives while the
  daemon is down is announced once when it starts again.
- **Polling a mailbox with nothing new** sends three IMAP commands, opens no
  new connection and writes nothing.

### MCP servers

- **Per-tool allow and deny.** `/mcp deny <server> <tool>` denies one tool for
  this session; `--keep` keeps the denial in the MCP config. `/mcp allow
  <server> <tool>` keeps an allow. `/mcp clear <server> <tool>` removes this
  session's denial and the kept rule, says which it removed and what decides
  calls now. Settings, the `/mcp` form, the daemon routes and the web UI's
  Settings > Permissions set them too. A rule applies at start and on change
  without restarting the server; a call not yet sent to a newly denied tool
  ends. An allow or clear is your own act: asked once, refused to the model,
  and an allow is never read from a project file.
- **MCP calls have deadlines** and report honestly when they time out; each
  server can set how long its tool calls may take, and a server that drops
  reconnects on its own.

### Tool calls and the turn

- **Independent tool calls run side by side.** Every provider request lets the
  model return several calls at once. Reads and read-only MCP tools run
  together; writes run together only when their paths do not overlap; `exec`
  and anything that needs you run alone, in the model's order. Results go back
  in the order the model issued them, one failure does not fail the others,
  and cancelling the turn cancels them all. `runtime.maxParallelToolCalls`
  (default 8) caps calls in flight. Both terminal apps show calls running at
  once.
- **Less common tools are sent as one line each**, with a tool to load a full
  definition on request, instead of riding in full on every request.
- **Model text appears as it arrives** in every mode. A draft the completion
  check rejects is withdrawn openly; after two rejections the answer is shown
  with what could not be verified.
- **Delegated work no longer blocks the composer**, and a runaway sub-agent
  stops at its turn or token bound.
- **The main session and worker agents share one turn loop**, so retries,
  hooks, budgets and notices behave the same everywhere. Tool hooks run for
  every tool call, including spawned agents and contract work, and a failing
  guard hook refuses the call.
- **A run killed while a command runs** restores that call as interrupted on
  `--continue`, with "effect unknown".

### Terminal apps

- **One print level** in both apps: `/mode quiet|balanced|operator` (alias
  `/hitl`) applies at once, notifications included.
- **The work plan is one store per project**, shared by the terminal app, the
  Agent, the daemon and every spawned agent (`~/.goodvibes/work-plans.sqlite`).
  `/work-plan` (aliases `/wp`, `/todo`, `/workplan`) and the `work_plan` tool
  read and edit it; an open Work Plan view follows edits made by another app.
  Done and cancelled items untouched for 30 days, or beyond the 200 most
  recent, are removed by the edit that finishes an item.
- **A cleanly saved session is no longer offered as a crash**, and Remove
  removes that one snapshot.
- **Typed characters in a settings screen go to search**; actions use Enter,
  Ctrl with a letter or a leader key. Retry and fix-session jump need Alt
  chords.
- **Command-line commands refuse options they do not take**, naming the ones
  they do. Free text after a slash command reaches it as typed, quotes and
  spacing included.
- **`!command`** runs through the shared shell code in both apps, and `#`
  notes are saved the same way.
- **Terminal commands that destroy something ask once before they run**;
  reversible command lines run at once in both apps.
- **Status and version start faster**; see [Speed](#speed).

### Web UI

- **One event stream per page** instead of six, so the browser's connection
  limit is not exhausted; a dropped stream fetches what it missed.
- **The command palette ranks locally and instantly**; no model is asked.
- **Messages queued behind a running reply** are shown in the chat view and can
  be edited or dropped there.
- **A pairing link signs in before the first request.**
- **Daemon errors show at once with their code**; a failed chat reply says it
  failed and why.
- **A Work Plan view** shows and edits the project's work plan; the Work page
  reads the owner inbox and refreshes it from the stream.
- **Running hosted sessions can be stopped**, and fleet processes stopped,
  interrupted and resumed.
- **The web UI says when its daemon is too old for it.**

### Daemon and operator API

- **Refusals carry one shape** over HTTP and WebSocket: a code, the state, the
  reason and the next step.
- **The daemon writes and refreshes its own service definition.** The
  installers run `goodvibes-daemon install-service` on a first install and
  `goodvibes-daemon refresh-service` on an upgrade; `service-status --json`
  names who wrote the definition. Every app finds the managed service in one
  place.
- **`goodvibes-daemon config set` writes daemon-owned settings again**
  (`controlPlane.port`, `payments.*`, `judgment.*` and the rest), and the daemon
  is the one writer of its settings file.
- **Apps on the daemon's own machine use the credential they already have**:
  `/work`, headless runs and the Agent need no pairing step there. Pairing stays
  for other devices.
- **Sessions are stored per session with messages appended**, not one file
  holding every transcript.
- **Triggers can be created and managed** by agents and the owner through the
  daemon, and record why they did or did not run.
- **A workspace move** rebuilds every service on the new root, or returns to the
  old one if the new one does not start.
- **Outbound deliveries that failed are kept as dead letters** that can be
  listed and replayed.
- **One table of exit codes** for every program is in
  [docs/exit-codes.md](https://github.com/mgd34msu/goodvibes/blob/v3.3.0/docs/exit-codes.md).

### Contracts, automation and knowledge

- **A failed contract unit asks you to retry or cancel** instead of ending the
  contract; finished contracts can be removed; budgets are enforced with one
  escalation; a retried contract start is recognised instead of starting
  twice; a contract resumed at start-up waits for the provider files.
- **A one-time schedule finishes**, and reminders and routine schedules are
  created once and never hang.
- **Worktrees** are removed at contract end when they hold nothing unique; a
  clean but unmerged worktree is pruned after 14 days.
- **The knowledge store is one SQLite file with one writer**, so a crash or a
  second process no longer risks the whole store; another process's commit is
  seen from the database itself.
- **A knowledge question asks the decision model once per source over a
  shortlist** the program made, instead of once per paragraph; listing
  knowledge asks nothing. Answers say what was left out and why.

### Settings

- **One way to write a settings file and one revision for it.** Start-up no
  longer rewrites old keys or moves settings and credentials between stores.
- **Setting descriptions say what the settings do.**
- **Card numbers and plain credentials are refused in settings** from every
  writer; card details an older Settings screen stored are deleted when the
  daemon starts.
- **New settings** include `judgment.decisionDeadlineMs`,
  `payments.confirmEveryPurchase`, `runtime.maxParallelToolCalls`,
  `sandbox.workspaceWritable`, `sandbox.egressAllowlist`,
  `fetch.allowedPrivateHosts`, `network.privateDeliveryHosts`,
  `notifications.webhookUrls`, `cluster.nodeName`, `cluster.peers`,
  `daemon.connectedHost.url`, `provider.visionFallbackModel`,
  `cloudflare.aiGatewayId`, `worktree.setup.commands`,
  `worktree.setup.carryOverGlobs`, the `checkpoints.*` guards,
  `surfaces.email.inbound.mailboxes`, the `*.inboxTagging` switches,
  `tools.validators.*` and `storage.secretProviders.*`.

## Removed

Each of these was retired by the owner; what does its job now is named.

- **Output modes** (`default`, `vibecoding`, `justvibes`). They did nothing.
  "Don't ask me questions" is `permissions.mode` `just-vibes`, and printing
  less is `/mode quiet`.
- **The `team`, `packet` and `worklist` tools** and their files. A team is an
  agent cohort (shown on each agent in the fleet), a brief is the spawn context
  and success criteria, and the model's checklist is the project work plan
  through the `work_plan` tool.
- **`payments.checkout.fillCard`** (the fill-card verb and route). The purchase
  the daemon runs types the card itself.
- **`goodvibes-daemon migrate-service`.** The installer still retires the old
  `goodvibes-daemon.service` unit.
- **`/triggers migrate`**, the trigger migrate operator method and the web UI
  migration form; `/triggers status` and the web UI panel inspect only.
- **The `config` form of `/mcp deny`.** `/mcp clear` lifts any rule on a tool.
- **`/policy promote --force`**, the divergence threshold and the trend sample
  command on the promotion path. `/policy simulate` shows the rule diff and the
  recorded calls the candidate bundle would decide differently; `/policy
  promote --yes` enforces it.
- **The feature flag `killed` state.** A locked managed setting forces a
  feature off and says why.
- **The model-ranked web UI command palette** (now local matching), and the
  model readings of small facts in the web UI (credential and card fields,
  reply prefixes, code language), now decided in code.
- **The state inspector** from the runtime observability entry.
- **The model picker's context-cap option** that did nothing, and the
  `vaporwave` theme name.

## Speed

Measured on one machine with the repository's measurement harness
(`bun run measure`), which counts decision-model requests, model requests,
file reads, writes, fsyncs, bytes written and SQL statements per scenario.
Before is the first commit of this work, one commit after 3.2.0; after is the
3.3.0 tree. Wall times are medians on that machine and will differ on yours;
the counts do not depend on the machine.

| Operation | Decision requests | File reads | Writes | SQL statements | Wall time |
| --- | --- | --- | --- | --- | --- |
| One ordinary read tool call | 1 to 0 | 2 to 1 | 0 to 0 | 5 to 0 | 15.0 ms to 4.7 ms |
| One command a remembered rule allows | 2 to 0 | 7 to 5 | 4 to 0 | 14 to 0 | 31.2 ms to 13.2 ms |
| A turn with twelve tool calls | 16 to 2 | 39 to 31 | 5 to 1 | 96 to 4 | 227.7 ms to 78.6 ms |
| A permission decision with 100 saved rules | 1 to 0 | 0 to 0 | 0 to 0 | 5 to 0 | 207.1 ms to 2.0 ms |
| A 200-record knowledge search | 200 to 24 | 2,038 to 0 | 0 to 0 | 1,800 to 47 | 10.4 s to 7.9 ms |
| Listing 200 knowledge records | 0 to 0 | 810 to 0 | 0 to 0 | 0 to 1 | 1,324 ms to 1.2 ms |
| An Agent route plan | 614 to 3 | 0 to 0 | 0 to 0 | 5,526 to 5 | 11.5 s to 42.7 ms |
| An Agent catalog search | 33 to 0 | 0 to 0 | 0 to 0 | 297 to 0 | 928 ms to 35.0 ms |

The two Agent rows were measured before on a 33-tool registry the harness
built itself, and after on the 81 tools the Agent starts with. The knowledge
search before made one decision request per record whatever the answer.

- **Session store.** A session heartbeat wrote the whole 3.75 MB store with two
  fsyncs; it now writes nothing. Appending a message wrote 3.75 MB; it now
  appends 239 bytes.
- **An inbound channel message** wrote 18.8 MB with 12 fsyncs; it now writes
  39.6 KB with 5.
- **An inbound email record** rewrote a 753 KB file; it now writes 509 bytes.
- **Saving contract progress** is one append of about 500 bytes whatever the
  size of its input.
- **Eight independent reads in one turn** finish within the harness's bound of
  twice the slowest read, not their sum.
- **Content search** with `rg` on `PATH` reads 6 files instead of 1,800 on a
  repeated search of the harness's 1,800-file project; a repeated file listing
  reads no directory again.

| --- | --- | --- |
| `goodvibes --version` | 1,472 ms | 329 ms |
| `goodvibes status` | 1,645 ms | 484 ms |
| `goodvibes-agent --version` | 983 ms | 323 ms |

## Security

These describe what changed, not how the earlier behaviour could be used.

- **Repository content cannot act for you.** Settings, services, secrets,
  hooks, MCP servers and trust markers inside a repository are limited as
  described under [Workspace trust](#workspace-trust-and-repository-content);
  a repository can no longer redirect the operator's private stores with a
  link, and its secret store can no longer read your own credentials.
- **Pairing and sign-in.** The pairing link and QR code no longer carry the
  shared operator token. Revoking a device revokes the tokens it minted and
  ends its open connections at once. Device tokens past the managed rotation
  age are refused. Sign-in has one handler with a per-address limit and hashes
  passwords off the event loop; a cross-site sign-in post and proxied or
  tunnelled requests no longer count as the owner's machine.
- **Access by role.** Signed-in users without the admin role no longer read
  the owner's transcripts, session titles, task prompts or private records, and
  event streams send each person only what their access allows.
- **Secrets stay out of model requests.** Credentials in commands, short
  passwords in commands or URLs, and credential-shaped words in memory text are
  recognised in code and never sent to a decision model. Typed passwords and
  client secrets stay out of the input history.
- **Network reach.** Fetch never reaches internal addresses in any mode unless
  the owner lists the host; a webhook sender's callback URL and a calendar
  feed cannot reach private hosts without the owner. Named service credentials
  go only to that service's own address.
- **Sandbox.** A sandboxed command's arguments and links no longer expose your
  home directory. An agent can narrow the sandbox lists, but only you can widen
  them. A remote command's environment can no longer swap the program that
  runs. Words that arrived by voice never run as a shell command.
- **Channels.** Teams verifies the Bot Framework token on each activity; a chat
  approval press with no readable sender is refused; only a channel's owner
  settles his purchase, approval or run.
- **Card material** is refused in settings from every writer and in chat
  replies, including a security code sent in reply to a purchase notice.
- **Plugins** have trust tiers that decide what a plugin may register and run,
  and plugin signatures verify against a publisher key you save.
- **At rest.** The telemetry ledger masks each line as it writes it, support
  bundles mask any field a setting's shape does not declare, and uploads are
  redacted by default.

## Known limits

- **Two published engine subpaths load only under Bun:**
  `@goodvibes-jev/engine/terminal-shell/wake-inference` and
  `@goodvibes-jev/engine/terminal-shell/audio/wake-runtime` (their wake-word
  runtime uses a Bun-only file import). Every other code subpath loads under
  Node as well.
- **The macOS service case is first verified in CI.** The launchd service
  commands act on the agent in the logged-in session's `gui/<uid>` domain; this
  is exercised by the macOS native CI jobs, not on a developer machine before
  release.
- **Features that only work with a decision model** say so when none is in use
  and do not offer a path without one: autonomous contracts and workstreams,
  Home Graph generated pages and answers, semantic knowledge answers, repair
  and enrichment, checkout interpretation, order-mail correlation and purchase
  replies, Google setup page automation, learning curation, gift planning,
  prose address reading, Decision Router categorization and task-route
  planning, compaction quality grading, tool-argument repair and ecosystem
  recommendations. With no decision model, a purchase inside your limits asks
  you instead of opening a veto window.
- **`goodvibes status` run in a separate process** shows a set decision model
  as in use even while the running app reports it failing; the running app,
  headless output and the web UI show the failure.
- **Content search without `rg` on `PATH`** reads the project's files on every
  query.
- **Internal identifiers** still use the word "classic" in a few stored values
  (`provenance: 'classic'` in knowledge, link-validation, screening and
  contract records) and in the `decisionPolicy.operation` value a tool result
  carries.

## Upgrade notes

No data migration from before this release is provided for the data this
release stopped reading: nothing converts it, and nothing deletes it unless a
note below says so. In practice, upgrading from 3.2.0:

- **Worktrees created by 3.2.0 are removed, with what they hold.** A worktree
  under a project's `.goodvibes/.worktrees` that has no created-by record (every
  worktree an earlier version made) is removed by the start-up retention sweep
  of the daemon and both terminal apps once no running owner holds it,
  including uncommitted changes. Its branch is deleted only when it is merged;
  commits the base lacks stay reachable on the branch. Commit or copy anything
  you want from those worktrees before upgrading.
- **Settings.** Check `permissions.mode` and `judgment.policy` (see the table
  above). Keys from earlier releases are reported as unknown and not used.
  Daemon-owned settings left in an app's settings file are not moved: set them
  again with `goodvibes-daemon config set`. Settings a project file may no
  longer set (anything that loosens safety or runs a command) are ignored from
  the project file; set them in your own settings if you want them.
- **Credentials** in another app's secret store are no longer lifted into the
  daemon at start; store each where the app that uses it reads it. A key in a
  project's secret store is used only after `/secrets trust`.
- **Not read any more**, and left on disk: the `team`, `packet` and `worklist`
  files; `queries.json` (the owner inbox has its own store, so open questions
  from 3.2.0 do not appear in it); `triggers-v2.json` and `triggers.json` (and
  action grants saved with the old checksum pin no longer fire); the Agent's
  `documents.json`; a per-surface `subscriptions.json` and an old
  `batch-jobs.json`; per-project plan files; `transcript-<id>.journal` files;
  the old shared `~/.goodvibes/recovery` directory and the pre-surface session
  layout; companion chats in the single-file `<id>.json` format; a session
  saved under the older file-naming rule.
- **Still opened and carried forward:** the daemon's 3.2.0 session store is
  moved to the per-session layout on first start (a copy of the old file is
  kept beside it with the suffix `.whole-store-backup`); a knowledge store from 3.2.0 opens in the
  current format, and a copy of the old file is kept; a legacy memory file is
  folded in once and renamed `memory.sqlite.folded`.
- **Going back to 3.2.0 after running 3.3.0 is not supported**: some stores
  this release writes cannot be read by the 3.2.0 programs.
- **Installers.** The installers no longer write a systemd unit or launchd
  plist themselves; they ask the daemon to, and `migrate-service` is gone.
- **Scripts.** Branch on exit codes with [docs/exit-codes.md](https://github.com/mgd34msu/goodvibes/blob/v3.3.0/docs/exit-codes.md).
  `goodvibes run` refuses an option it does not take (exit `2`).
- **API consumers.** Refusals now arrive in one shape (code, state, reason,
  next step) over HTTP and WebSocket; `payments.checkout.fillCard` and the
  trigger migrate method are gone. Regenerated contracts and API records are in
  `packages/engine/contracts/` and `packages/engine/etc/`.

## For contributors

- **Tests.** The suites were rewritten to a small set kept for money,
  permissions, messages, stores, the turn loop, contracts, the installer and
  the decision model: 151 test files (4,053 at 3.2.0): 142 in the default
  suite with 475 cases, 5 sandbox proofs, 2 end-to-end runs of the built
  programs and 2 web UI browser journeys. Every test file opens with the risk it proves and the change that
  turns it red, recorded in `packages/engine/docs/test-risks.md`. The runner
  enforces 5 seconds per test and 10 per file and refuses sleeps, timer waits,
  snapshots, module mocks, skips and retries.
- **CI.** `bun run validate` runs the same steps CI runs, job by job
  (`--job gates|build|typecheck|proofs|live-sandbox|measure|package`). The
  push workflow runs 12 jobs instead of about 40, and the repository has 7
  workflows instead of 9. Validation compiles the engine once.
- **Speed budgets.** `bun run measure:check` fails on a count above its budget;
  see `AGENTS.md`.
- **Decision calibration.** `bun packages/engine/scripts/project-calibration.ts
  --gate` writes the gate calibration record the default mode reads.
- **Model catalog.** Model prices, limits and failover links come from one
  pinned models.dev snapshot; `bun packages/engine/scripts/model-catalog-pin.ts`
  moves the pin when a release is cut.
