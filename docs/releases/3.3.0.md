# GoodVibes 3.3.0

GoodVibes 3.3.0 asks you far less and answers far faster. A read, a search, an
edit inside the workspace and a command a saved rule covers start at once, with
no model request and no question. You are asked only what is yours to decide,
and the answer is remembered. The calls in between are judgment calls for Jev,
the decision model, each with a deadline and a fallback so nothing hangs. One
setting, `permissions.mode`, chooses how much you are asked; one setting,
`judgment.policy`, chooses whether a decision model is used and what happens
when it fails.

The release also finishes the owner inbox, purchases within your limits,
per-tool MCP rules, parallel tool calls and the shared work plan, adds
`goodvibes acp` for editors and `goodvibes-daemon mcp serve` for MCP clients,
and closes a long list of security gaps.

## Before you upgrade

- **Worktrees made by 3.2.0 need nothing from you.** At every start the
  daemon, `goodvibes` and `goodvibes-agent` clean up worktrees under a
  project's `.goodvibes/.worktrees`, but one with uncommitted or untracked
  changes is never removed automatically, whichever version made it. Each start
  lists what was removed and every worktree kept for your decision, with the
  commands to save, keep or discard it (see [Contracts and
  knowledge](#contracts-and-knowledge)).
- **Your `judgment.policy` choice keeps its meaning.** A saved `Classic - Off`
  is read as `No Decision Model`, `Default - On` as `Decision Model Only` and
  `Preferred` as `Hybrid`; the settings file is not rewritten. If you never
  saved a value, the default is now `Hybrid`, which continues without the
  decision model when it fails; the 3.2.0 default stopped. Choose `Decision
  Model Only` to keep stopping.
- **A repository's `hooks.json` and MCP files run nothing until you trust the
  workspace.** A hook or MCP server you rely on from a project's own files
  stays off in an undecided workspace; the app says so once at start, and
  `/trust workspace trusted` turns them on at once.
- **Card details an older Settings screen stored stay in the secret store.**
  This release does not remove them and no purchase reads them. Delete them
  with `goodvibes secrets delete <name>` for each of
  `GOODVIBES_PAYMENTS_CARD_NUMBER`, `GOODVIBES_PAYMENTS_CARD_EXPIRY`,
  `GOODVIBES_PAYMENTS_CARD_CVV` and `GOODVIBES_PAYMENTS_CARDHOLDER_NAME`
  (`goodvibes secrets list` shows which are there). Cards added with
  `/payments card` are kept separately and are not affected.
- **Settings notices are printed when a program starts**: an old value read
  under its new name names both, and a key this release does not know is
  reported as unknown. They go to the terminal and the activity log; for the
  daemon running as a service, to the service's log.

The rest of what upgrading means for stored data is under
[Upgrade notes](#upgrade-notes).

## Who decides: permission modes

`permissions.mode` has four values. The default is `jev-decides`.

| Mode | What happens |
| --- | --- |
| `ask-me` | Jev reads each judgment call's risk. Calls it reads as critical, irreversible or security-weakening ask you, with owner-only items; the rest run. |
| `jev-decides` | Jev decides judgment calls; owner-only items ask you. With no working decision model it behaves as `ask-me`. |
| `just-vibes` | Nothing interrupts you. Jev decides judgment calls when a decision model works; anything that needs you is held and listed at the end of the run, where `/held` approves or sets it aside. |
| `yolo` | The permission gate asks you nothing except about a change asked for from a channel. Authentication, workspace containment, secret storage and spending limits still apply, and an act only you perform (answering an approval, granting access) is refused to the model. |

`plan` remains a separate read-only posture.

- **Owner-only items.** In `ask-me` and `jev-decides` these come to you; in
  `just-vibes` they are held and listed at the end of the run. Jev never
  answers one, whether or not a decision model is set (with `No Decision
  Model` too, and with `permissions.tools.exec` set to `allow`). In `yolo` they
  run without asking, except your own acts (answering an approval or a
  purchase window, granting or withdrawing access), which an agent is always
  refused.
  - Granting access: pairing, MCP trust or role, channel allowlists, hooks, and
    tools declared dangerous.
  - A change that loosens a security, judgment or payment setting.
  - A call your own "always ask me" rule covers, and a change asked for from a
    channel conversation.
  - Deleting or overwriting something nothing keeps a copy of. The program
    recognises this itself in shell commands (`rm`, `unlink`, `shred`,
    `wipefs`, `mkfs`, `dd` to an output, `truncate`, `find -delete` or
    `find -exec rm`, `git clean`, `git reset --hard`, `git checkout --` or
    `git restore` over files, a forced or deleting `git push`, `git branch -D`,
    `git stash drop` or `clear`, `git worktree remove --force`, removing Docker
    or Podman volumes, a database client dropping or truncating a table), also
    when run through `sudo`, `env`, `xargs`, `timeout`, `sh -c` and the like; in
    an exec file operation that deletes or overwrites; and in operator methods
    that cannot be undone, such as deleting schedules, memory records,
    sessions, payment cards or calendar events, or ending a hosted session. A
    decision model that reads another call as destroying something with
    confidence also sends it to you. A command that might wipe the machine or
    your data wholesale is asked for that one call; nothing is offered to
    remember.
  - Sending as you to a new recipient: a webhook URL, mail address, calendar
    attendee or delivery address chosen in the call that is not one of your own
    destinations (your mail addresses, notification webhooks, the Google Chat
    webhook, and the Signal, WhatsApp and telephony default recipients) and
    that you have not allowed this session or with a remembered rule. The
    program reads the recipient itself in the tools that declare one (channel
    sends, review packet shares and drafts to a webhook, Gmail send, schedules
    and reminders with a delivery webhook, operator calls that mail, invite or
    deliver), in shell commands that mail (`mail`, `mailx`, `sendmail`,
    `msmtp`, `mutt`, `swaks`, the Twilio CLI) or post to a messaging service
    with `curl`, `wget` or HTTPie, in `fetch` requests to a messaging service,
    and in MCP or plugin tools that name a mail address or phone number in
    `to`, `cc`, `bcc`, `recipients` or `attendees`. The messaging services are
    Slack, Discord, Google Chat and Microsoft Teams webhooks, ntfy, Telegram
    bots, Twilio, SendGrid, Mailgun, Postmark, Resend, the Slack and Microsoft
    Graph send APIs and the Gmail API. A send whose recipients it cannot read
    (`sendmail -t`, a body read from a file) is treated as a new recipient. A
    send to a channel or route you set up, or to your own web surface, is not
    a new recipient.
  - Sending content derived from untrusted text read in the same turn.
  - Changing what a contract requires: replying to a contract's question and
    changing a running contract's budget.

  Spending is not on this list: a purchase over a limit you set, and a payment
  step (a card security code, 3-D Secure, a CAPTCHA), are put to you through
  the purchase window in every mode, `yolo` included. What the program cannot
  recognise stays an ordinary judgment call: an address or URL held in a shell
  variable, a config file or a piped list, a message sent from inside a script
  or program the agent runs, a post to a service not in the list above, an MCP
  tool that addresses by a channel or user id, and anything typed into a web
  page or app by the browser, computer or device tools.

- **The default and calibration.** The shipped `jev-decides` hands decisions to
  Jev only when the endpoint, the model and every fallback target that can
  answer them are the ones the shipped calibration measured: the hosted
  endpoint and `jev-latest` (answered by `jev-1.14.0`), passing on all 49
  decisions in the gate's calibration set. Otherwise it works as `ask-me` until
  you choose `jev-decides` yourself: in Settings or `/permissions`, with
  Shift+Tab, for a hosted session, or in a channel profile. A session's choice
  survives a daemon restart.

- **Shift+Tab** in the terminal app changes the mode of the current session
  only; the saved default stays in `/permissions` and Settings. Entering `yolo`
  this way asks once first. The key is the rebindable `cycle-permission-mode`.
- **`--just-vibes` and `--yolo`** pick a mode for one launch of `goodvibes`
  without changing settings.
- **`/decisions`** lists what Jev decided for you at the permission gate. For
  each one you can undo it (files the call changed are restored when its tool
  recorded them), turn it into a standing rule (never, always, or always ask
  me), or keep it.
- **`/held`** lists what `just-vibes` held instead of asking, and approves or
  sets aside one item or all of them. A call held in a session the daemon
  hosts (a web UI chat, for example) is also put in the owner inbox.
- **A call routed to you is asked or held, never approved in your name.** The
  terminal app's exec sandbox settles an ask only when the permission gate
  marked it containable, and that answer is recorded as the sandbox's, not
  yours.
- **Every tool result that is not a plain success carries one decision
  object** with its state, who decided, the reason and the next step.

## Decision model policy

`judgment.policy` has three values.

| Value | When the set decision model fails |
| --- | --- |
| `Hybrid` (default) | The operation continues without it: each decision takes its stated fallback, and you are told once, naming the model, what failed and the next step, and once again when it answers. |
| `Decision Model Only` | Work that needs the model stops and reports the model, what failed and the next step. |
| `No Decision Model` | No decision-model request is made. |

- **With no decision model set** (no `judgment.endpoint`, `judgment.model`,
  `judgment.fallbacks`, credential choice, `TYPESAFE_API_KEY`,
  `TYPESAFE_BASE_URL` or `TYPESAFE_DEFAULT_MODEL`), every policy runs without
  one: nothing is asked, nothing waits, nothing reports an error. A fresh
  install works before any decision model is configured.
- **You can always tell when no decision model is in use.** The conversation
  says so once; `goodvibes status`, `goodvibes doctor` and
  `goodvibes-agent status` print a "Decision model" section; a headless run
  prints the line on stderr and adds `diagnostics.decisionModel` to its JSON
  result without changing the exit code; the web UI shows it in a bar under
  the header.
- **Deadlines.** A decision that you or a tool call wait on gets one request
  bounded by `judgment.decisionDeadlineMs` (default 1500 ms) and takes its
  fallback when the model is off, slow, unavailable or unsure. A decision
  target that misses its deadline three times in a row is skipped for a
  minute. A target that refuses the connection is not asked twice.
- **Outages are reported as outages.** A rejected key is reported as rejected
  with its status; "rate limited" is said only for HTTP 429.
- **Features that only work with a decision model** say "No decision model is
  in use, so this part is not available" instead of failing. Over the daemon
  API they answer 409 `DECISION_MODELS_DISABLED` with what to do instead.

How much you are asked under each combination of policy and mode is in the
[decision model policy guide](https://github.com/mgd34msu/goodvibes/blob/v3.3.0/docs/decision-model-policy.md#how-much-you-are-asked).

## Speed

Measured on one machine with the repository's measurement harness
(`bun run measure`). Model and decision-model requests are answered by a
stand-in that replies at once and the network is blocked, so wall times are the
product's own overhead and exclude model latency; each decision request saved
also saves one real round trip. Before is the first commit of this work, one
commit after 3.2.0; after is the 3.3.0 release commit. Wall times are medians
on that machine and will differ on yours; the counts do not depend on the
machine.

| Operation | Decision requests | File reads | Writes | SQL statements | Wall time |
| --- | --- | --- | --- | --- | --- |
| One ordinary read tool call | 1 to 0 | 2 to 1 | 0 to 0 | 5 to 0 | 15.0 ms to 4.4 ms |
| One command a remembered rule allows | 2 to 0 | 7 to 5 | 4 to 0 | 14 to 0 | 31.2 ms to 13.2 ms |
| A turn with twelve tool calls | 16 to 2 | 39 to 31 | 5 to 1 | 96 to 4 | 227.7 ms to 62.0 ms |
| A permission decision with 100 saved rules | 1 to 0 | 0 to 0 | 0 to 0 | 5 to 0 | 207.1 ms to 1.9 ms |
| A 200-record knowledge search | 200 to 24 | 2,038 to 0 | 0 to 0 | 1,800 to 47 | 10.4 s to 8.9 ms |
| Listing 200 knowledge records | 0 to 0 | 810 to 0 | 0 to 0 | 0 to 1 | 1,324 ms to 1.5 ms |
| An Agent route plan | 614 to 3 | 0 to 0 | 0 to 0 | 5,526 to 5 | 11.5 s to 38.1 ms |

The route plan was measured before on a 33-tool registry the harness built
itself, and after on the 83 tools the Agent starts with. Eight independent
reads in one turn finished in 1.4 times the slowest read, not their sum.
Appending a message to a session writes 239 bytes instead of rewriting a
3.75 MB store, and an inbound channel message writes 39.6 KB instead of 18.8 MB.

Start-up of each program run from source with bun, spawn to exit, median of
three runs after one warm-up:

| Command | Before | After |
| --- | --- | --- |
| `goodvibes --version` | 1,472 ms | 317 ms |
| `goodvibes status` | 1,645 ms | 483 ms |
| `goodvibes-agent --version` | 983 ms | 314 ms |
| `goodvibes-agent status` | 1,432 ms | 482 ms |
| `goodvibes-daemon --version` | 966 ms | 322 ms |
| `goodvibes-daemon serve`, to its ready line | 2,542 ms | 1,623 ms |

## What changed

### Editors and other clients

- **`goodvibes acp`** runs GoodVibes as an Agent Client Protocol agent over
  stdio from the installed program, for editors that launch an agent server
  (Zed and others): `{ "command": "goodvibes", "args": ["acp"] }`.
- **`goodvibes-daemon mcp serve`** serves a running daemon's operator methods
  to an MCP client over stdio. By default it serves the sessions, tasks,
  contracts and approvals methods that read, plus creating a session, sending
  it a message and steering it; `--categories` picks other families, and
  methods that change state or are marked dangerous are served only with
  `--allow-write` or `--allow-destructive`.

### Workspace trust and repository content

- **A repository's `hooks.json` and MCP files run nothing until you trust the
  workspace.** In both terminal apps, a `hooks.json` inside an untrusted
  workspace is not loaded, and the MCP servers its `.mcp/mcp.json` or
  `.goodvibes/mcp.json` name do not start or replace yours. An undecided
  workspace counts as untrusted. Your own hooks and MCP files are not affected.
  The Agent gains `/trust workspace trusted|restricted`.
- **Trust decisions live in your own workspace register**, keyed by the
  directory's real path; a trust file inside a project has no effect. An
  undecided workspace raises one question that stays open until answered;
  reads run meanwhile, and after ten minutes unanswered, later writes, commands
  and delegation are refused at once with the next step instead of waiting
  again.
- **A project settings file sets only display, behaviour, contract, worktree
  and stricter permission settings.**
- **A project's `services.json` adds only services whose credentials are keys
  in your secret store**; command references and sign-in blocks come only from
  your own file. A project's secret store is read only at the project root, and
  a key in it is used once you confirm it with `/secrets trust`.

### Purchases

- **Limits default to 0, and the first time a purchase meets one you are
  offered the chance to set it.** `payments.budget.dailyItem` and
  `payments.budget.perPurchaseCeiling` start at 0, so by default every purchase
  asks you. The first time a purchase meets one of them at 0, the owner inbox
  asks for the amount and the daemon writes your answer to the setting.
- **Inside your limits the agent buys without asking.** It opens a veto window
  (`payments.windows.vetoMinutes`, default 10): the notice is in your owner
  inbox and on the channels in `payments.notifyChannels`, one word (stop)
  cancels it, and silence lets it go ahead.
- **Outside your limits it stops and says which limit and by how much**, for
  example "comes to USD 30.00 and is over the per-purchase ceiling of USD 20.00
  by USD 10.00", and opens an approval window
  (`payments.windows.approvalMinutes`, default 60) where silence denies.
- **With no decision model in use**, a purchase is put to you as an explicit
  approval that lists what was not checked; silence never buys.
- **Pre-approval of every purchase is optional and off by default**
  (`payments.confirmEveryPurchase`). An approval given in advance from the web
  UI's Purchases panel or `/payments approve` still answers its window.
- **Limits apply to the full total**, a card's declared issuer cap and
  `payments.defaultCardId` apply, and a total that changed at checkout is not
  submitted.
- **The order is submitted once.** An ambiguous click is reported as submitted
  with its outcome unknown and is never retried; the budget stays reserved
  until the order is confirmed or reconciled.
- **A purchase waiting on you survives a daemon restart**, and its notice goes
  to every channel in `payments.notifyChannels`, not only Telegram.
- **Scheduled purchases** can buy what you authorised in advance:
  `/payments standing add` sets the item, shops, per-purchase and per-period
  maximums and an optional last day.
- **The Agent can start and cancel purchases again.**
- **eBay purchases** read the listing: auctions and Best Offer are refused, and
  the two seller thresholds (`payments.ebayMinSellerFeedbackCount`,
  `payments.ebayMinSellerPositivePercent`) decide whether a Buy It Now purchase
  proceeds on silence or asks first.

### One owner inbox

- **One owner inbox per home** (`~/.goodvibes/shared/owner-inbox.sqlite`) that
  the daemon, both terminal apps and every running copy read and answer at
  once. A question asked in one app shows in all of them; an answer given
  anywhere reaches the asker on its next model request, with no restart.
- **An agent can leave you a question and carry on** (the `query` tool). You
  answer with `/questions` (alias `/inbox`) in either terminal app or in the
  web UI's Work page.
- **Contract questions wait in the owner inbox**: a failed unit's retry or
  cancel question, the "accept the unchecked result" question and any other
  question a contract asks. A reply given elsewhere withdraws the item.
- **A message from a sender not on a channel's allowlist** is held as one inbox
  item per sender instead of being dropped; accepting adds the sender to the
  allowlist.
- **An answer typed in a terminal app is recorded as answered there.**

### Mail

- **Mail inbox rows carry a screening field.** Each row says `screened`, or
  `not-screened` with the reason (no screening route, no decision model in
  use, or a screening failover). The subject stays exactly as received. The
  terminal app's `/mail list` tags such rows `[not screened]`, the Agent's
  unified inbox says so, and the web UI mail view shows a "Not screened" chip.
- **Mail reaches the mail inbox without a screening route.** Without screening
  consent or credentials, the email inbox is built unscreened instead of being
  unavailable; a plaintext mailbox is accepted on a loopback host only.
- **Each arriving message is announced and recorded once**, also across a
  daemon restart; mail that arrives while the daemon is down is announced once
  when it starts again.
- **Polling a mailbox with nothing new** sends three IMAP commands on the held
  connection, opens no new connection and writes nothing.

### MCP servers

- **Per-tool allow and deny.** `/mcp deny <server> <tool>` denies one tool for
  this session and only ever tightens; `--keep` keeps the denial in the MCP
  config. `/mcp allow
  <server> <tool>` keeps an allow in your own MCP config; an allowed tool is
  not held to the server's path and host scope. `/mcp clear <server> <tool>`
  removes this session's denial and the kept rule, and says which it removed
  and what decides calls now. Settings, the `/mcp` form, the daemon routes and
  the web UI's Settings > Permissions set them too. A rule applies without
  restarting the server. An allow or clear is your own act: asked once,
  refused to the model, and never read from a project file.
- **Each MCP server can set how long its tool calls may take.**

### Tool calls and the turn

- **Independent tool calls run side by side.** Reads run together; writes run
  together only when their paths do not overlap; `exec` and anything that
  needs you run alone, in the model's order. Results go back in the order the
  model issued them, one failure does not fail the others, and Ctrl-C cancels
  them all. `runtime.maxParallelToolCalls` (default 8) caps calls in flight.
  Both terminal apps show calls running at once.
- **Less common tools are sent as one line each** instead of riding in full on
  every request. The model's first call to one returns its full definition
  without running, and the tool is sent in full from then on.
- **A run killed while a command runs** restores that call as interrupted on
  `--continue`, saying whether it took effect is unknown.
- **The browser tool's start has its own 20-second deadline.** When a browser
  does not finish starting in time, the call ends with an error that names the
  browser it waited for, whether its process started or ended, the last lines
  it printed and the next step (call `launch` again; if it stops the same way,
  `provision` with `repair:true`), and the browser's processes are ended.
- **Reading a page whose script is stuck ends after 15 seconds** (a snapshot,
  an extract, a scroll), with the reason and the next step (`navigate` or
  `screenshot`), instead of holding the call.

### Terminal apps

- **One print level** in both apps: `/mode quiet|balanced|operator` (alias
  `/hitl`).
- **Notices that need you show on the main screen in both apps**, at start-up
  too: errors, warnings, offers such as restoring an unsaved session, a
  settings value that was ignored or read under its new name, update results
  and start-up faults. Routine system and tool lines stay in the Activity view
  (Notifications in `goodvibes`). Setting `ui.systemMessages` or
  `ui.operationalMessages` to `panel` yourself keeps those notices there too,
  except errors, warnings and anything waiting for your answer, which always
  show. Start-up notices also appear as toasts, and a burst of toasts waits its
  turn instead of pushing earlier ones off.
- **The work plan is one store per project**, shared by the terminal app, the
  Agent, the daemon and every spawned agent (`~/.goodvibes/work-plans.sqlite`).
  `/work-plan` (aliases `/wp`, `/todo`, `/workplan`) in the terminal app,
  `/workplan` in the Agent, and the `work_plan` tool read and edit it. Done and
  cancelled items untouched for 30 days, or beyond the 200 most recent, are
  removed by the edit that finishes an item.
- **Typed characters in a settings screen go to search**; actions use Enter, a
  Ctrl chord or the `Ctrl+G` leader key.
- **Command-line commands refuse options they do not take**, naming the ones
  they do (exit `2`).
- **`status` and `--version` start much faster**; see [Speed](#speed).

### Web UI

- **A tab holds at most two live event connections** (one for app-wide
  updates, one for an open session's detail), so the browser's connection
  limit is not exhausted.
- **The command palette matches locally**; no model is asked.
- **Messages queued behind a running reply** are shown in the chat view and can
  be edited or dropped there.
- **A pairing link signs in before the first request.**
- **A Work Plan view** shows and edits the project's work plan; the Work page
  shows the owner inbox.
- **A running hosted session can be stopped.**
- **The web UI says when its daemon is too old for it.**

### Daemon and operator API

- **Daemon refusals carry a code** and, where the daemon knows them, the state
  and the next steps.
- **The daemon writes and refreshes its own service definition.** The
  installers run `goodvibes-daemon install-service` on a first install and
  `goodvibes-daemon refresh-service` on an upgrade.
- **`goodvibes-daemon config set` writes daemon-owned settings**
  (`controlPlane.port`, `payments.*`, `judgment.*` and the rest).
- **Apps on the daemon's own machine use the credential they already have**:
  `/work`, headless runs and the Agent need no pairing step there. Pairing stays
  for other devices.
- **Sessions are stored per session with messages appended**, not one file
  holding every transcript.
- **Notifications that could not be delivered are kept** and can be listed
  and sent again (`notifications.deadLetters.list` and `replay`).
- **One table of exit codes** for every program is in
  [docs/exit-codes.md](https://github.com/mgd34msu/goodvibes/blob/v3.3.0/docs/exit-codes.md).

### Contracts and knowledge

- **A failed contract unit asks you to retry or cancel** instead of ending the
  contract, and its progress survives a daemon restart; a finished contract can
  be removed (`contracts.remove`).
- **Worktrees are cleaned up at every start, never at the cost of unsaved
  work.** One made by an earlier version is removed only when it has no
  uncommitted or untracked change and every commit on it is on a branch or in
  the base; removal is never forced. Commits on a detached HEAD that no branch
  holds are first saved to a new branch, `goodvibes/saved-<first 12 characters
  of the commit>`, and then the folder is removed. A branch is deleted only when it is merged. A worktree's own
  ignored files (other than `node_modules`, `.venv` and unchanged copies of the
  main checkout's files) are kept for 14 days after it was last used, then
  removed with it. A worktree is left alone while its contract, workstream item
  or contract input is still running, while it is locked with
  `git worktree lock`, while it was used in the last 10 minutes, while another
  worktree sits inside it, or while it is marked kept or paused or attached to a
  session or task.
- **Every start shows on the main screen of both terminal apps what was
  removed** and lists each worktree kept for your
  decision with its path, why it was kept, and three commands: save it (commit,
  on a new branch when HEAD is detached), keep it as is
  (`git worktree lock <path>`, which also stops the listing), or discard it
  (`git worktree remove --force <path>`). The daemon writes the same lines to
  its log, prefixed `[goodvibes-daemon] worktrees:`. The same list is in
  `/status` in both terminal apps and, in `goodvibes`, in `/worktree review`.
- **The knowledge store is one SQLite file** that several processes read and
  write; another process's commit is seen by the next read.
- **A knowledge search asks the decision model about a shortlist** the program
  made, not every record; listing knowledge asks nothing.

### Settings

- **Start-up no longer rewrites old keys** or moves settings and credentials
  between stores; a key this release does not know is reported as unknown.
- **Card numbers and plain credentials are refused in settings** from every
  writer.
- **New settings you may want:** `judgment.decisionDeadlineMs`,
  `payments.confirmEveryPurchase` and `runtime.maxParallelToolCalls`.

#### Settings whose names or values changed

| Setting | In 3.2.0 | In 3.3.0 | What an old value does now |
| --- | --- | --- | --- |
| `permissions.mode` | `safe-owner` (default), `safe-jev`, `yolo`, `plan` | `ask-me`, `jev-decides` (default), `just-vibes`, `yolo`, `plan` | Read as the new value, and the file is not rewritten: `safe-owner`, `prompt`, `normal`, `accept-edits` and `custom` as `ask-me`; `safe-jev` and `auto` as `jev-decides`; `just-work` as `just-vibes`; `allow-all` as `yolo`. `prompt`, `normal`, `accept-edits` and `custom` also print a notice saying so. A saved value counts as your choice of mode. |

## Removed

- **Output modes** (`default`, `vibecoding`, `justvibes`). They did nothing.
  Not being interrupted is `permissions.mode` `just-vibes`, and printing less
  is `/mode quiet`.
- **The `team`, `packet` and `worklist` tools.** A team is an agent cohort
  (shown on each agent in the fleet), a brief is the spawn context and success
  criteria, and the model's checklist is the project work plan through the
  `work_plan` tool.
- **`payments.checkout.fillCard`.** The purchase the daemon runs types the card
  itself.
- **`goodvibes-daemon migrate-service`.** The installer still retires the old
  `goodvibes-daemon.service` unit.
- **`/triggers migrate`** and the trigger migrate operator method;
  `/triggers status` inspects only.
- **The `config` form of `/mcp deny`.** `/mcp clear` lifts any rule on a tool.
- **The feature flag `killed` state.** A locked managed setting forces a
  feature off and says why.
- **Model readings of small facts in the web UI** (palette ranking, credential
  and card fields, code language): decided in code.
- **The state inspector** from the runtime observability entry.

## Security

- **Repository content cannot act for you.** Settings, services, secrets,
  hooks, MCP servers and trust markers inside a repository are limited as
  described under [Workspace trust](#workspace-trust-and-repository-content);
  the operator's private stores and credentials are read only from the
  operator's own locations.
- **Pairing and sign-in.** A pairing link or QR code pairs one device and
  carries nothing else. Revoking a device revokes the tokens it minted and ends
  its open connections at once. Sign-in is limited per address, and only a
  direct connection from the same machine is treated as the owner's machine.
- **Access by role.** Each signed-in user reads only what their role allows, in
  requests and in event streams.
- **Secrets stay out of decision-model requests.** A call whose arguments hold
  a credential is never sent to the decision model: in `ask-me` you are asked,
  and in `jev-decides` and `just-vibes` the gate refuses it with the reason.
- **Network reach.** Fetch reaches a private-network host only when you list it
  in `fetch.allowedPrivateHosts` or admit the call; cloud-metadata, link-local
  and other reserved addresses stay refused.
- **Sandbox.** A sandboxed command does not see your home directory, also not
  through a link in the workspace. An agent can narrow the sandbox lists, but widening them
  is yours. A remote command runs the program named, with a fixed environment.
- **Channels.** Teams activities are authenticated on every request, and an
  approval pressed in a chat is accepted only from an identified owner.
- **Card material** is refused in settings from every writer and in chat
  replies, including a security code sent in reply to a purchase notice.
- **Plugins** have trust tiers that decide what a plugin may register and run;
  `goodvibes plugin trust` sets one.
- **At rest.** The telemetry ledger masks each line before it is written, and
  support bundles withhold any value whose field they do not know.
- **Dependencies.** The glob-matching library used by the build tools and the
  bundled language servers is patched so that a crafted pattern can no longer
  stall them, and the dependency audit fails if any installed copy lacks the
  patch.

## Known limits

- **Two published engine subpaths load only under Bun:**
  `@goodvibes-jev/engine/terminal-shell/wake-inference` and
  `@goodvibes-jev/engine/terminal-shell/audio/wake-runtime` (their wake-word
  runtime uses a Bun-only file import). Every other code subpath loads under
  Node as well.
- **Features that only work with a decision model** say so when none is in use
  and do not offer a path without one: autonomous contracts and workstreams,
  Home Graph generated pages and answers, semantic knowledge answers, repair
  and enrichment, checkout interpretation, order-mail correlation and purchase
  replies, Google setup page automation, learning curation, gift planning,
  prose address reading, Decision Router categorization and task-route
  planning, compaction quality grading, tool-argument repair and ecosystem
  recommendations. With no decision model, a purchase inside your limits asks
  you instead of opening a veto window.
- **`goodvibes status` run in a separate process** shows a set decision model
  as in use even while the running app reports it failing; the running app,
  headless output and the web UI show the failure.
- **Content search without `rg` on `PATH`** reads the project's files on every
  query.
- **On Apple Silicon Macs, stopping or restarting the daemon can occasionally
  end in a crash instead of a clean exit.** In our CI we observed it once in 26
  shutdown checks. It happens after shutdown has begun (on Ctrl-C,
  `stop-service`, `restart-service` or an update handover); the shell or the
  service log shows "trace trap" and macOS writes a crash report to
  `~/Library/Logs/DiagnosticReports`. The cause is inside the runtime the daemon
  is built on and is not yet identified; it is being tracked for the next
  release. If the daemon is not running afterwards, start it again
  (`goodvibes-daemon start-service`); no repair step is needed, and its
  SQLite stores recover an interrupted exit when they next open. In the crash
  we observed, the daemon's work before the stop had already been saved;
  whether a write still in progress at that moment could be lost is not yet
  known.
- **On macOS**, if the daemon service does not start after the upgrade, run
  `goodvibes-daemon service-status` and `goodvibes-daemon refresh-service`,
  then `goodvibes-daemon start-service`.

## Upgrade notes

No conversion is provided for data this release stopped reading: it is left on
disk, unread. In practice, upgrading from 3.2.0:

- **Settings.** Check `permissions.mode` and `judgment.policy` (see the table
  above). Keys from earlier releases are reported as unknown and not used.
  Daemon-owned settings left in an app's settings file are not moved: set them
  again with `goodvibes-daemon config set`. Settings a project file may no
  longer set are ignored from the project file; set them in your own settings
  if you want them.
- **Credentials** in another app's secret store are no longer lifted into the
  daemon at start; store each where the app that uses it reads it. A key in a
  project's secret store is used only after `/secrets trust`.
- **Not read any more, and left on disk:** the `team`, `packet` and `worklist`
  files; `queries.json` (open questions from 3.2.0 do not appear in the owner
  inbox); `triggers-v2.json` and `triggers.json` (triggers from 3.2.0 are not
  loaded); the Agent's `documents.json`; an old `batch-jobs.json` (batch jobs
  from 3.2.0 are not loaded); the work plan's per-project JSON files (the work
  plan starts empty); a per-app `memory.sqlite` that was never folded into the
  shared memory store (`.goodvibes/tui/memory.sqlite`,
  `~/.goodvibes/agent/memory.sqlite`, `.goodvibes/goodvibes/memory.sqlite`);
  `transcript-<id>.journal` files; the old shared `~/.goodvibes/recovery`
  directory and the session layout from before per-app folders; companion
  chats in the single-file `<id>.json` format; a session saved under the older
  file-naming rule; a sign-in kept only in an app's own `subscriptions.json`
  rather than the shared one (sign in to that provider again if it is not
  listed).
- **Opened and carried forward:** the daemon's session store is moved to the
  per-session layout on first start, with a copy of the old file kept beside it
  with the suffix `.whole-store-backup`; the daemon's inbound mail records are
  moved into the new store and the old file is removed; a knowledge store from
  3.2.0 is upgraded in place after a copy is taken under `snapshots/` beside
  it; sign-ins in the shared `subscriptions.json` are moved into the secret
  store when first read.
- **Going back to 3.2.0 after running 3.3.0 is not supported**: some stores
  this release writes cannot be read by the 3.2.0 programs.
- **Installers.** The installers no longer write a systemd unit or launchd
  plist themselves; they ask the daemon to, and `migrate-service` is gone.
- **Scripts and API consumers.** Branch on exit codes with
  [docs/exit-codes.md](https://github.com/mgd34msu/goodvibes/blob/v3.3.0/docs/exit-codes.md).
  `payments.checkout.fillCard` and the trigger migrate method are gone.
