# GoodVibes 3.3.1

GoodVibes 3.3.1 makes OpenAI one provider with two ways of signing in, takes
every model list from the provider itself, and stops a failed turn from moving
to a model you did not choose. It also replaces credential-shaped sample values
in the product's own fixtures with generated placeholders.

## Before you upgrade

- **`openai-subscriber` is gone; change any setting that names it to
  `openai`.** A saved `provider.model` such as `openai-subscriber:<model>` is
  not rewritten for you. At start, `goodvibes` and `goodvibes-agent` say
  "Configured model '...' is unavailable; using '...' this session. Your saved
  model is unchanged." and run on the first model in their list for that
  session only; a daemon turn fails with an error naming the model. Set it to
  `openai:<model>`, or pick the model again with `/model`. Any other setting
  that names an `openai-subscriber:` model must be changed the same way.
- **A ChatGPT sign-in made with 3.3.0 keeps working.** It was already stored as
  OpenAI's; you do not need to sign in again.

## OpenAI: one provider, two sign-ins

A ChatGPT subscription and an OpenAI API key are two ways of signing in to the
one `openai` provider, with one model list.

- Requests use the subscription when it is set up, otherwise the API key.
- With both set up, a request the subscription fails (sign-in ended, plan
  limit or rate limit, a model the plan does not serve, a server or network
  error) is asked again of the same model through the API key, before any
  output has reached you. The turn tells you once which sign-in answered and
  why: "... is answering through your openai API key: the ChatGPT subscription
  failed (...). The same model is in use; this sign-in is billed its own way."
  `goodvibes run` writes the same line to stderr and reports the sign-in that
  answered on its usage and turn-result output.
- A model the subscription does not list, or refused this session, goes to the
  API key first when one is set.
- With no sign-in at all, nothing is sent and the error says how to sign in
  (`/subscription login openai start`, or an `OPENAI_API_KEY`).
- Usage served by the subscription is recorded as subscription use with no
  per-token price; API-key usage is priced as before.
- Embeddings and the Batch API need the API key. With only a subscription they
  refuse and say so.
- The model picker shows one row per OpenAI model and the sign-in order in its
  detail. In the web UI, Settings > Models > OpenAI shows the same order.

## Model lists come from the provider

No provider keeps a list of models in the program any more. A provider's list
is what its own endpoint answers, else its last answer saved on disk, else the
pinned model catalog's rows for it. OpenAI reads its API list and, when signed
in with a subscription, the plan's own list, and merges them; a model it lists
that the catalog does not know yet can be selected the day it ships, marked
unclassified. A model you type that no list names is still sent, and a refusal
is shown as the provider gave it.

Lists are read in the background, never on a request's path: at start (a list
saved less than a day ago is used without a request), after you sign in or
out, when a model list is opened (the same one-day rule), when a provider
refuses a model as unknown (at most once a minute per provider), and, in
`goodvibes`, on `/refresh-models`, which reads every provider's list again at
once.

## Failover no longer picks a model for you

In 3.3.0 a failed turn could move to a different, older model chosen by its
place in the model list. Now:

1. The same model on another sign-in of the same provider is tried first
   (OpenAI: the subscription, then the API key), inside the request.
2. Then only your own order, the new setting `provider.fallbackModels`: a list
   of provider-qualified models, for example `["anthropic:claude-sonnet-5"]`,
   empty by default. The first entry not yet tried this turn whose provider is
   signed in is used, and the notice names its place in your order.
3. Otherwise the turn stops and says why nothing else was tried, with the next
   step: retry, choose another model with `/model`, or set
   `provider.fallbackModels`.

A turn in which a tool had already started is never resubmitted. Synthetic
failover groups, which you choose as a ladder of backends for one model, work
as before.

## Status and doctor

`goodvibes status`, `goodvibes doctor` and `goodvibes-agent status` now show,
for the configured model's provider, the sign-ins in the order requests use
them (for example `sign-in: subscription, then API key (OPENAI_API_KEY)`) and
where the model list came from: the provider's own listing with its age and
size, or the pinned model catalog when the provider has not listed its models
yet. These reports read files only, so a key stored with `/secrets` is not seen
by them, and the line says so.

## Security

- Sample values in the product's own fixtures and proofs that looked like real
  credentials (API keys, tokens, a card number) are now generated placeholders
  or published test values, and the project's checks refuse a
  credential-shaped value anywhere in its source.
- One of those values had the shape of a Telegram bot token and was present in
  the 3.3.0 source and binaries. It is not a working token: Telegram's API
  answers 401 Unauthorized for it. No action is needed from you.

## Known limits

- **On Apple Silicon Macs, stopping or restarting the daemon can occasionally
  end in a crash instead of a clean exit.** It was observed once in 32 shutdown
  checks in our CI up to the 3.3.0 release (the 3.3.0 notes said once in 26).
  It happens after shutdown has begun (on Ctrl-C, `stop-service`,
  `restart-service` or an update handover); the shell or the service log shows
  "trace trap" and macOS writes a crash report. The cause is inside the runtime
  the daemon is built on and is not yet identified. If the daemon is not
  running afterwards, start it again (`goodvibes-daemon start-service`); no
  repair step is needed.
- **Not verified against OpenAI's live service:** the exact shape of the
  ChatGPT subscription's model list and the wording of its refusal for a model
  the plan does not serve were written without access to a real subscription
  and are not confirmed. A refusal of that kind sent as "not found" is always
  asked again through the API key; one sent as a bad request is asked again
  only when its wording names the model as unknown or unsupported, and
  otherwise the turn shows the refusal as OpenAI gave it.
- The other limits listed in the 3.3.0 notes still apply: two engine subpaths
  load only under Bun, features that need a decision model say so without one,
  `goodvibes status` in a separate process can show a failing decision model as
  in use, and content search without `rg` reads the project's files on every
  query.
