# GoodVibes 3.3.2

GoodVibes 3.3.2 changes how the programs look and talk to you more than any
patch release before it. The first run is three steps. Every ask is one card
worded as a question. Every slash command opens a short list of what it can do
and a form for the blanks, and many commands were folded into others, so the
list of commands is shorter and each has one name. Every setting is shown by a
name that says what it does. The web UI signs in with a cookie a page script
cannot read, and approvals carry a revision so a stale answer is refused.

It also keeps more of what you would otherwise lose: answers owed to a chat,
messages that arrive during an update, and every item of every list.

## Before you upgrade

- **Many slash commands were removed, renamed or folded into another
  command, and every short alias is gone.** A command you type from habit may
  now be refused. [Removed and renamed commands](#removed-and-renamed-commands)
  lists each one with what to type now. In the terminal app, a lone word one
  slip from a command name is refused with the command it probably meant; any
  other word starts a prompt.
- **`/config` is `/settings`.** `/settings` opens the settings screen, and
  `/settings list`, `get`, `set` and `reset` work on a setting by its key.
- **In the Agent, `Ctrl+P` opens the list of everything you can do; the
  workspace is `Ctrl+G`.** `Ctrl+O` and `F2` open Your agents, which replaces
  the Activity panel.
- **The web UI asks you to sign in once more.** It no longer reads the sign-in
  an earlier version kept in the browser's storage; it signs in with a cookie
  instead (see [Security](#security)). The old entry
  (`goodvibes.webui.token`) is left in the browser and is not used; clearing
  the site's data removes it. A device token stays valid until you revoke it
  (`/devices revoke`).
- **A model can no longer run `/managed apply`, `/settings-sync pull` or
  `/services trust`.** Each is marked on the command's first screen as
  loosening a protection; type it yourself.
- **A webhook address or an ntfy topic can no longer be written into a
  settings file as plain text.** `/notify add <url>` stores a webhook address
  in the secret store and saves a reference to it. An address an earlier
  version saved in `notifications.webhookUrls` is still sent to.
- **API clients:** approval actions now require `expectedRevision`, several
  list methods page with a cursor, `email.inbox.update` requires
  `uidValidity`, and six MCP and schedule methods were renamed. See
  [For client authors](#for-client-authors).

## First run in three steps

`goodvibes` and `goodvibes-agent` run the same first run. It opens only when
the model the session would use is not ready; with a key for the default
model's provider already set (`OPENROUTER_API_KEY` for the default
`openrouter:openrouter/free`), the first start asks nothing.

1. **Which model should answer you?** A ChatGPT subscription (sign in with your
   browser), Anthropic or OpenRouter (paste an API key), a model on this
   computer (the scan of this computer, never the network, says what it found:
   `found <server> with <n> models`), or `Another provider…`. When a key in the
   environment already makes a provider usable, `a` uses it and skips step 2.
2. **Sign in or paste the key.** A key is stored in secure storage and checked
   with one request to the provider; a key the provider refuses is removed
   again and the step says so. A browser sign-in shows the address to open if
   the browser did not open, and takes a code when the provider ends on one. A
   local model server lists its models with their size where the server
   reports it.
3. **The conversation.** Under the splash: `You're set.  Answering with
   <model>`, three starting prompts for the folder (Tab puts the next one in
   the empty composer), and one sentence saying what GoodVibes asks before
   doing, for the permission mode in force. The starting prompts show on every
   empty conversation, not only the first.

Esc on step 1 sets up later and writes nothing. `/setup` lists the setup
topics and opens one form per topic; the long wizard with its step rail is
gone. `/setup` → `Run first-run again` opens the three steps again. After
first run the splash names the model in use. Notices wait until the first
message is sent instead of drawing over the splash.

## The approval card

Every ask, in the terminal app, the Agent, the web UI and chat channels, is
worded once by the daemon and drawn the same everywhere:

- The title is the question in a sentence: `Run this command?`, `Change a file
  outside this folder?`, `Turn <setting> off?`; a purchase names the item, the
  shop and the price, and a send names the person it goes to. The folder it
  runs in is on the right, and `1 more waiting` when others wait behind it.
- Under it: what the call acts on (every command in full, the paths, the
  address), the change itself for a write or an edit, and one sentence saying
  what it will do.
- The question is red, with `This can't be undone.`, only for a call known to
  be irreversible. There are no risk chips. With no decision model, the
  details say that GoodVibes cannot tell whether it can be undone.
- Keys: `y` yes once, `n` no, `a` yes and remember (when remembering is
  offered), `d` details, any other typing starts a reason for refusing.
  **Enter presses the selected button, which is `No` for anything that cannot
  be undone and for money spent, a payment step or a message sent as you.**
- Nothing that cannot be undone can be remembered; the card says `always asks
  · can't be remembered`.
- Refusing no longer cancels the turn: the model is told the call was refused,
  with your reason, and the turn goes on.
- A question an agent left for you appears as `A question for you` above the
  composer; it needs no permission, and Esc answers later (it stays in
  `/questions` and the web UI).
- A purchase names its item, shop, price and currency. `/questions withdraw`
  takes back a request for approval you raised. Leaving plan mode asks first.

## The status bar and notices

The status bar under the composer starts with `Asks:` and the permission mode
you chose. When the mode in force differs, it says so and why: `Asks: Jev
decides · asking you for now · no decision model chosen`. Then context, branch
and model; a click on each opens its view (the mode opens the permission
setting, context the context inspector, branch the changes, model the model
picker).

`Shift+Tab` changes the mode for the session in both programs (the Agent gained
it). The change flashes the bar and writes nothing into the conversation.

Notices no longer take over the bar. They collect as a count (`2 notices`),
and `Ctrl+N` opens them. Start-up notices go into the same count. In the Agent,
a scheduled run that failed while it was closed is named in one sentence at
start, and the bar no longer shows a sleep hold during a turn.

## Your agents, and Work in the web UI

The terminal app and the Agent share one panel, **Your agents** (`F2`,
`Ctrl+O` or `/agents`). In the Agent it replaces the Activity panel.

- **Waiting for you** comes first: each row names the agent and what it asks
  (`● Helper agent   Run bun test?   just now`). Enter brings its card to the
  front.
- Then each running agent with what it is doing, the agents that finished this
  session, and **Scheduled** (schedules and watches with their cadence and
  last run; a day with calendar events has a line that opens them).
- The platform's own heartbeats, pollers and code index are behind one line,
  `Background services  N healthy ›`, and never counted as running. An
  unhealthy one is listed by itself.
- `s` stops an agent and what it started (it asks first), `n` starts a new
  one, `p` pauses or resumes a schedule. An opened agent's view scrolls back to
  its first row.

The web UI's **Work** view is grouped the same way: Waiting for you, Running
now, Scheduled and Finished, with background services behind one line.
Questions waiting for the owner appear there. An approval a chat is waiting on
appears inside that chat with Approve and Deny. Each tool call reads as one
line, with the raw data behind Details, and tool activity survives a reload.

## A failed turn

A failed turn is one row in the conversation under your prompt, which stays as
you typed it:

```text
✕ The model didn't answer.
  OpenAI returned an error (500) six times. Nothing was changed.

  alt+r try again   alt+o use another model   alt+i details
```

The second line says who failed, how often it was tried, and what the turn's
tools changed before it stopped (`2 files were changed before it stopped.
/changes`; `Nothing was changed.` only when the record shows nothing was
written, run or sent). `alt+i` shows the provider's own message and why no
backup model was tried. A provider that refused its key offers `alt+s sign in
again`. While no backup model is set, a tip names `/model backup`. A turn sent
with no usable model is refused before any request is made. Alt keys now work
in terminals without the kitty keyboard protocol, tmux included. The web UI
shows a failed turn as a row with what to do next.

Commands report what happened the same way: a command that did nothing, failed
for every item or was refused by the daemon exits with an error and says which
part failed, and a message sent in parts reports how many arrived.

## Every slash command is guided

Typing a command alone opens a short list of what it can do; an action with
blanks opens a form, a step at a time, with `This will run:` showing the line
it builds as you type. Before anything changes, one sentence says what is
about to happen; afterwards the program prints what happened, how to undo it
and `The command for this is: <line>`. A typed line that leaves a blank out
opens the form at that blank. A secret typed into a form is never printed
back. The same descriptions drive completion, help, the confirmation, the web
UI's sheets and what the model is told about each command. On a small terminal
a form scrolls to keep the focused blank visible.

`?` on an empty prompt, `/help` and `Ctrl+P` open one list of everything you
can do in both programs, with the keyboard shortcuts at the end. The separate
help overlay and shortcuts overlay are gone; `/help` prints a command's actions
when you name the command.

Text you type is kept as typed: `--yes` inside a message, note or answer is
part of the text for every guided command, words after `--` are literal, and
a message that contains `--yes` no longer skips the question before sending.

Commands gathered into one:

- `/session`: resume, save, copy, rename, search, delete, save as a file
  (keys and paths hidden unless asked; an existing file is kept unless you say
  to replace it), upload for a link (always asks first), branches, the task
  graph, and looking through the conversation (find, next and previous error,
  expand, collapse, bookmarks). `/resume` and `/save` stay as their own
  commands.
- `/settings`: the settings screen at a topic or setting, and list, get, set
  and reset by key.
- `/health`: one line saying everything is working, or the problem with the
  line that fixes it; failure reports, the runtime store and compatibility are
  its actions.
- `/security`: trust, policy and the sandbox.
- `/provider`: sign-in, your own providers, routing and moving sign-ins.
  `/model refresh` says for every provider how many models it found or why its
  list could not be read.
- `/agents`: hosting, teams, delegation and hand-off. `/work`: asking for work,
  importing it and planning.
- `/channels` (both programs), `/mail` (To, subject and message), `/devices
  pair` (a device, this terminal, a relay device or a chat channel),
  `/checkpoint` (list, make, restore, rewind), `/media` (make and collect
  images and video), `/voice` (speaking and wake setup), `/notes` (the same in
  both programs), `/web-search`, `/secrets`, `/memory`, `/usage` (cost is part
  of it) and `/changes` (the diff).
- `/mcp` blocks and unblocks tools, `/schedule` pauses and resumes schedules,
  and `/triggers` sets a trigger up from a form instead of JSON.
- `/cloudflare provision` asks before deploying anything that can be billed.
  `/documents readiness`, `packet-steps` and `timeline` print what is ready,
  what is missing and the line that fixes it.
- The Agent gained the terminal app's code lookups (`/intelligence`), hooks,
  plugins, undo and checkpoints, and commands of its own for documents,
  artifacts, model comparison and research (`/documents`, `/artifacts`,
  `/compare`, `/research`), so nothing its workspace could do became
  unreachable.

### The Agent workspace

The workspace (`/agent` or `Ctrl+G`) opens the same guided forms the slash
commands open: each of its rows names a command action, and its side pane says
what the selected row does and shows that command's own report. Browsing it
never reaches the network: a report that reads a mailbox, a provider or the
daemon runs only when you press `Ctrl+R`. Its pane is readable on a small
terminal.

## Every setting has a plain name

Each of the 655 settings is shown by a name that says what it does, with its
key as small text beside it, and `/settings` finds a setting by that name. A
setting that is
ignored is reported once, in one wording. A settings search with no result
says so once.

## Web UI

- **Sign-in** leads with scanning the code from `goodvibes pair`; a code,
  link, token or username and password are under `Other ways to sign in`. A
  code that names another daemon address is not sent to this one; the page
  offers to open that daemon instead. A daemon that answers the check with a
  server fault shows "The daemon could not answer" and keeps your code.
- **The mode chip.** The line of internal text above the app is replaced by a
  chip in the header that names the permission mode in force (`Jev decides ·
  asking you for now` while no decision model works). Opening it says why in
  one sentence, with `Change`. The no-decision-model notice is this chip and no
  longer pushes the page down.
- **Settings > Permissions** opens with the four modes as cards, each saying
  what it does; picking one sets `permissions.mode`.
- **Library > Knowledge** shows subjects and what is known about each, each
  fact with where it came from and when.
- **Guided sheets.** Every command action the daemon can run opens a sheet:
  the action's blanks as pick-lists, switches and fields, the sentence of what
  will happen, and `From a terminal:` with the line that does the same. The
  command palette (`Ctrl+K` or `⌘K`) lists each action by its label. An action
  only a terminal can do is shown greyed, with the reason.
- **The schedule editor.** A schedule described in words (`every weekday at
  9am`) is read by the daemon and shown back (`Read as: ... Next run: ...`)
  before it is kept; the button keeps exactly that reading. "Watch for
  something" works the same way. Schedules, MCP servers and tools, Repeat
  purchases and Triggers each have a screen.
- The badge, the header, the account menu and Work agree while a hosted
  session answers. The account menu's "Earlier notices" lists every toast the
  page showed. Earlier answers and decided approvals are listed under "Your
  answers" with "Show older". A working daemon on this machine is not reported
  unreachable when the network is down.

## Approvals

- **Every approval has a revision.** An approve, deny, claim or cancel names
  the revision it was shown; a stale or late one is refused with the current
  state, so two answers cannot cross. An approval is saved before anyone can
  see it. Acting on an approval right after raising it is no longer refused.
- Each viewer gets the same reading of an approval: what is waiting, who can
  act, what they can do now, and whether the requester received the decision.
  An answer to the owner is marked delivered only once the model request
  carrying it was accepted, and is handed over again if the process holding it
  stopped.
- **Answer from any node.** In a group of daemons, an approval raised on one is
  listed on the others (`<id>@<node>`) and can be answered there. The daemon
  that owns it applies the answer once, recorded as decided by
  `<person>@<node>`. A node that does not answer within 5 seconds is reported
  as unknown (`NODE_UNREACHABLE`), never as done or failed.
- What a person approved or refused, with the reason, is kept for good and
  paged; so are device grants given or ended.
- Two people's identical requests for approval are kept apart.

## Groups of daemons share one authority record

In a group (`goodvibes-daemon cluster create` and `cluster join`), one shared
record, the authority record, carries the members, key generations, device
tokens, sign-in users, device grants, peer tokens, passkeys, push
subscriptions, the day's payment spend, schedules, reminders and URL watchers.
A device paired on one machine works on all of them, and a revoke on any
machine refuses it everywhere and ends its open streams. Key rotation and
removal settle in any order. A machine that was away longer than
`cluster.revocationRetentionMinutes` takes the group's record before it acts,
so it cannot bring back what was revoked meanwhile. Purchases and scheduled
work run on one elected machine. `authority.status` and `cluster status` show
the record's revision and which members differ. A username that exists as two
accounts on two machines is reported, and `cluster publish user:<name>` keeps
one.

## Security

- **The web UI signs in by cookie.** Signing in by code, QR, link, token or
  password sets an HttpOnly, SameSite=Strict cookie (`Secure` over HTTPS) that
  no page script can read; nothing token-shaped is written to browser storage.
  A request from another site that would use the cookie is refused. Over the
  relay, the sign-in and the relay pairing live only as long as the page: a
  reload asks for them again. The phone-as-device credential has its own
  cookie, sent only to the device routes. Signing out of the web UI ends the
  daemon session, and the page is served with a content security policy.
- **Secrets stay in the secret store.** Notification webhook addresses and ntfy
  topic names are kept there, with only a reference in settings. Every stored
  value prints as `[secret NAME]` and is read only by a call that names its
  purpose; sign-in tokens print as `[secret]`. A value typed at a hidden
  prompt never reaches undo, history or search. Telemetry sent to a collector
  leaves out task text.
- **Card details are refused over a plain network connection** before anything
  else reads them; they are accepted over loopback, HTTPS or the machine's
  Tailscale address.
- **The browser tool checks every request.** The agent's browser refuses
  private and metadata addresses for every request a page makes, not only the
  first, including a browser the agent attaches to, and a page cannot start
  loading before the check is active. The new setting `browser.network.pinned`
  (off by default) fetches every page request from the address that passed the
  check, so a name that later resolves to a private address is refused; it
  costs a copy of every response through GoodVibes.
- **A chat set up for review can never grant ownership.** A message in a
  delegated chat is held for review whoever sent it, and nothing a sender does
  there raises an offer to make them the owner or to allow them. People
  admitted to a chat channel act as guests whose actions the owner approves.
- **Credentials in rootless containers.** The folder check for the credential
  and pairing stores accepts a parent folder owned by a user the container
  cannot act as, and still refuses one others can write to.
- Attaching to someone else's hosted session no longer makes you an owner of
  it; a session is shared on purpose with the share action
  (`sessions.hosted.share`).
- Changing where a credential is sent is refused unless the same change states
  the credential. A sign-in token is sent only to the daemon it belongs to. A
  confirmation applies only to what was shown, and a long one must be read to
  the end. A passkey can be registered only by the device it was offered to.
  Plugin trust belongs to one copy of a plugin and its content.
- A daemon narrowed to this machine stops serving the network at once.
  Loopback requests never go through a proxy. A setting that loosens security
  needs the owner. Relay codes are revocable per device.
- A method called through the generic invoke route or the WebSocket is checked
  against the same caller as its REST route, and every daemon route states who
  may call it.
- Voice audio and installer downloads refuse unsafe destinations. Formatters,
  linters and benchmark checks run contained where the sandbox is available.

## Reliability

- **Answers and messages survive a restart.** An answer owed to a chat channel
  is recorded before it is sent and sent again after a restart, under the same
  identity where the channel can drop a repeat. Webhook messages, Slack
  commands, web chat posts and scheduled deliveries survive a kill right after
  they were acknowledged. A message in a chat set up for review waits after a
  restart, and the owner inbox says a message is waiting. A steered message
  whose claim reply was lost is delivered exactly once. A message that may have
  been sent is kept and never sent again by itself.
- **When an answer is lost, the product says so and does not repeat the
  action.** A repeated request keeps one key. A settings change whose answer
  was lost is read back once and reported as done or unknown. A Cloudflare
  token whose creation timed out is found and revoked before another is made.
- **The update hold.** Before an update, nothing starts new work: WebSocket
  calls, chat channel messages, schedules, watchers, triggers, sweeps, GitHub
  events, store snapshots and memory consolidation all wait. A channel message
  that arrives during the hold is kept and answered once after the restart; a
  schedule due during the hold runs once after it. Reads still answer. The
  daemon does not move to a new version while it cannot tell whether a turn is
  running, and a "yes" to proposed work keeps the direction typed with it.
- **Nothing is lost past a count.** Chats, session messages, inbox answers,
  mail drafts, command output, notices, open sessions and artifacts are no
  longer cut off at a number; lists page back to the first item ("Show older"
  in the web UI).
- **One owner at a time.** Two programs starting the same keyed contract start
  it once. A session open in one terminal is not overwritten by another. A
  stopped schedule, watcher or run cannot start or deliver anything afterwards.
  A contract killed as its first group starts resumes instead of failing.
- **A stop reports what is still running.** Stopping an automation run, an MCP
  or language server, an ACP agent or the tunnel connector waits for the
  process to exit, kills one that ignores the request, and names anything it
  could not end. Closing the terminal window is not recorded as a crash.
- Owner notices reach the owner's direct conversation on Slack, Discord, Google
  Chat, Matrix, Teams, BlueBubbles, iMessage, Home Assistant, SMS and
  Mattermost; a mail notice with nowhere to go lands in the owner inbox.
- A damaged checkpoint found at start is reported to the next terminal or web
  UI with what to do. An undo on a full disk leaves the file whole. A rewind or
  a reverted change is refused when the conversation or file changed after the
  preview. Memory sync no longer deletes files when the store read was cut
  short. Knowledge enrichment finishes a pass that stores a fact. Mail changes
  are refused when the folder was rebuilt since the list was read. Each
  occurrence of a recurring calendar event has its own id, and an event edited
  elsewhere since it was opened is not overwritten.

## Failover

With a backup model set (`/model backup`, or `provider.fallbackModels`), a
model answering with a server error is retried once after 2 seconds and then
the turn moves to the backup; it used to wait over two minutes. A server asking
to wait longer than that is not waited for.

Nine model calls made outside a turn now fail over the same way, each for that
one call: compaction's summary and its distilled brief, the helper and tool
models, the check-in note, native work intake, knowledge enrichment, image
understanding and the private verification proposal. Image understanding moves
only to a model that reads images and stays local when the reading is local.

## Speed

- Raising and answering an approval writes 1.5 KB where it wrote 121 KB: each
  change appends one record instead of rewriting the whole store.
- A chat message costs one write fewer: it no longer rewrites the chat's
  summary.
- Opening the Agent workspace runs one database statement where it ran
  sixteen, and reads 51 fewer facts.
- The web UI no longer makes an extra request per approval to word it.

## Other changes you may notice

- **Purchases name their currency**, and budgets and spending carry it. A
  purchase is marked bought only with evidence from the merchant; a purchase
  restored after a restart keeps its item and shop; prices read the same
  everywhere. An unreadable answer to a purchase buys nothing.
- **A password ending in a space is kept as typed.**
- **The command line refuses a lone unknown word** (`goodvibes foo`) instead of
  opening the app, and words after `--` are taken literally.
- The terminal app no longer edits the project's `.gitignore`.
- `/compact` says when there is nothing to compact, and made media names the
  program that made it.
- Memory search no longer mixes vectors from different embedding models and
  says how many memories wait to be re-embedded. A recompiled document drops
  its outdated links. A daemon's discovered local models reach sessions already
  running.
- Both terminal programs share one updater and one update timeout setting, and
  one rules file.
- `/permissions never` adds a rule that a command is never run; the gate
  enforces it in every mode.
- Scheduled runs can read mail and calendar and deliver their answer.
- LM Studio: the stateful chat continuation is removed; a message without tools
  no longer leaves a stored copy of the chat in LM Studio.
- The installer takes `--no-auto-update` (or `GOODVIBES_AUTO_UPDATE=0`) to keep
  every program from updating itself from the first launch, and `--from-dir
  <dir>` (or `GOODVIBES_RELEASE_DIR`) to install from a directory holding the
  release files, with no request to GitHub. An install removes only files it
  recorded putting there.
- Mail's mark-read works again after the mail server rebuilds a folder, and
  mail sign-in over STARTTLS works.

## Known limits

- **Plugins run inside the program.** A plugin's trust tier decides what it
  is offered; it is not a sandbox. A plugin's code runs with the program's
  access.
- **The patched glob dependency is not bundled for npm consumers.** This
  repository patches every `picomatch` it installs against
  GHSA-fc5q-39xc-vjpf, which has no fixed release. An application that installs
  the engine package with the optional language servers gets an unpatched
  `picomatch` 2.x unless it applies the same patch (see
  [SECURITY.md](../../SECURITY.md)).
- **Benchmark verification is not isolated on macOS, on native Windows, or on
  Linux without bubblewrap.** The verify script then runs on the host with the
  task directory writable, and the result says `verification was NOT
  isolated`.
- **No kept test covers the browser tool's per-request checks.** The checks
  are in place as described above; nothing in the test suite turns red if they
  break.
- **On Apple Silicon Macs, stopping or restarting the daemon can occasionally
  end in a crash instead of a clean exit.** This is unchanged from 3.3.1: it
  happens after shutdown has begun, the shell or service log shows "trace
  trap", and the cause is inside the runtime the daemon is built on. If the
  daemon is not running afterwards, start it again (`goodvibes-daemon
  start-service`).
- The other limits listed in the 3.3.0 and 3.3.1 notes still apply.
