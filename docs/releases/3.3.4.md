# GoodVibes 3.3.4

GoodVibes 3.3.4 makes the daemon's own update finish when the old daemon
cannot finish stopping, and stops reporting a handover that worked as a
failure. Nothing you have stored changes, and an installed 3.3.3 updates to it
as usual.

## Updates

- **An update whose old daemon cannot finish stopping still hands over.** The
  orderly stop before the handover now ends after a minute; the old daemon
  then exits and the service manager starts the new release. Each step of the
  stop is logged as it starts, so the log names the step that held it.
- **A handover that worked is no longer recorded as a failure.** On every
  update under systemd, the service manager's stop of the old daemon (the
  restart that was asked for) was taken for a cancelled handover: the daemon
  recorded the handover as incomplete, said automatic updates were paused, and
  recorded it twice. That stop is now recognised as the restart under way.
  The same holds for a rollback's restart. A receipt still waiting to be shown
  is no longer recorded a second time.

## Service commands

- **`service restart` waits long enough.** A start, stop or restart may now
  take up to two minutes, long enough for the daemon's own orderly stop,
  before it is reported as not finishing.
- **A command cut short says so in words,** for example that it did not finish
  within so many seconds or was ended by a signal before it reported a result,
  instead of `command exited with null`.

## Work

- **A contract that can be neither started nor cancelled is no longer retried
  without pause.** It stays waiting and is not driven again until it is
  released, and a warning is logged with why.

## Approvals

- **"Allow and remember" saves the rule before the approval shows as approved.**
  The rule used to be written just after, so something reading the approval at
  that moment could find no rule yet. If the rule cannot be saved, the approval
  is not recorded, the ask stays open, and the approver is told why
  (`REMEMBER_NOT_SAVED`).

## Known

- In one observed case, a 3.3.1 daemon used a full processor core after it
  installed an update. The cause was not found. What now bounds it: the stop
  before the handover ends after a minute, so the old daemon exits and the new
  release starts, and the log names the stop step that was still running.
