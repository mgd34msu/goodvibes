# GoodVibes 3.4.0

GoodVibes 3.4.0 is about saying what really happened. Where a step could not
be finished, a send may already have gone, or a file could not be read, the
programs now say so with the reason and the next step, instead of reporting
success, retrying on their own, or quietly starting over. Where an answer was
lost, a repeat finds the first result instead of acting twice.

It also brings the Agent level with the terminal app on daemons elsewhere: it
dials the address you give it, https included, pairs and unpairs its host
from `/devices`, and has `/plugin` and `/hooks`.

## Before you upgrade

- **Both terminal programs refuse a daemon older than 3.3.2** (it was 3.1.2).
  `goodvibes` and `goodvibes-agent` call `inbox.answer`, `mcp.servers.reload`,
  the MCP trust, role, quarantine and tool-block methods, `relay.codes.*` and
  `automation.schedules.pause`, `resume` and `preview`, which a daemon older
  than 3.3.2 does not serve. Update the daemon first.
- **The Agent no longer dials another machine named only by
  `controlPlane.host`.** Set `daemon.connectedHost.url` to the daemon's origin
  (`https://...` for an encrypted connection, or `http://...` to send this
  Agent's credentials unencrypted). Until then the Agent refuses before
  anything is sent, and the refusal gives the value to set. `/setup
  connect-daemon` writes it.
- **The Agent's `/plugin-trust` is `/plugin`.** It is the same command as in
  the terminal app; there is no other name.
- **Removed setting: `push.subscriptions.sweepIntervalMinutes`.** It is gone
  from `/settings` and the web UI. A value left in a settings file is kept and
  reported as an unknown key, and nothing reads it.
- **The release installer can now exit 4** (see [Installing and
  updating](#installing-and-updating)); a script that treated any non-zero exit
  as a failed install should read 4 as "installed, with problems".
- **API clients:** `TOKEN_EXPIRED` is gone from the error codes (it was never
  sent; an expired credential is answered `AUTH_REQUIRED`), and code built on
  the exported daemon HTTP transport must pass `expectedRevision` to the
  approval actions. See [For client authors](#for-client-authors).

## Connecting to a daemon on another computer

- **`/setup connect-daemon`** ("Use a daemon on another computer") is a new
  setup topic in both programs. It points the program at a daemon already
  running elsewhere and opens nothing on this computer to the network. The
  `browser` and `other-devices` topics no longer show the daemon-source rows.
  Every message that used to say "/setup, Network step" now names `/setup
  connect-daemon`, and so does `/accounts sign-in daemon`.
- **The Agent dials one address.** It uses `daemon.connectedHost.url` when set,
  with its scheme, else this machine's daemon, over https when that daemon's
  TLS is on. Next steps that told you to fix `controlPlane.host` or
  `controlPlane.port` now name `daemon.connectedHost.url`.
- **`--runtime-url` and `GOODVIBES_AGENT_RUNTIME_URL` accept `https://`** and
  set `daemon.connectedHost.url` for that one run.
- **Pairing the Agent with a host.** A preview of an interrupted pairing to
  another machine never sends this machine's daemon token; it offers to forget
  the attempt and says why it was not repeated. A pairing cancelled before it
  was sent leaves nothing behind.
- **The Agent's `/devices`** now pairs, shows and unpairs its host (`pair
  host`, `host-status`, `unpair-host`) and handles the relay (pair, status,
  codes, revoke), the same flows as `/setup pair` and `/setup unpair`.
- A record the host does not have (a 404 naming a missing session or item)
  reads as "no such record" with the host's own next step, instead of "this
  command is not wired up" or "the host runs a different version", in both
  programs.
- Daemon refusals read by the cluster and status commands show the daemon's
  own next step.
- The live verifier finds the daemon's real port and scheme from the daemon's
  own settings.
- Endpoint displays show the normalized host mode (`Network` shows as
  `network`). An unrecognized `httpListener` or `web` host mode reads as
  "read as local, this computer only (127.0.0.1:<port>)"; an unrecognized
  control-plane mode says the daemon does not start until it is corrected. The
  address shown for a daemon about to start follows the same bind rule
  (127.0.0.1 for `local`, even with a custom host left over).
- Approvals and credential writes made by the Agent are recorded as coming from
  the Agent, not the web UI.

## The terminal app

- **Starting on a session.** A `--resume`, `--continue` or `--fork` that cannot
  open its session prints `[Resume] Could not resume session <id>: <reason>`
  (`resume and fork` for `--fork`) and the app starts as a plain launch. Bare
  `--fork` now resumes the last session of the folder (the one `--continue`
  opens) and then forks it; nothing is forked when the resume fails.
- **Closing the window or sending SIGTERM** stops running `!` commands, `/test`
  runs and task processes, and the app exits 143 (SIGTERM) or 129 (SIGHUP).
- **A message sent while a `!` command runs** shows "Waiting for `!<cmd>` to
  finish ...; Esc stops it." and goes with that command's output, in order.
  This holds for typed and spoken messages, in both programs.
- An ask cancelled or answered elsewhere leaves the approval queue.
- `/test` started while a stopped run is still finishing is refused: "A test
  run is still going, or still finishing after a stop; Esc stops it, then run
  /test again once it has ended."
- `/session save-file` and upload no longer claim an upload or a copy that did
  not happen: the line says `(not uploaded)` or `(upload unconfirmed)`, and
  `(could not copy the path)` when the clipboard refused.
- `/schedule add` whose answer was lost does not create a second routine:
  "It may have been created; /schedule list shows it. Running the same line
  again will not create a second one."
- **A session is written by one terminal at a time**, in both programs. A
  session open in one terminal cannot be opened, saved or deleted from a
  second; the second is refused (`SESSION_OPEN_ELSEWHERE`) with what to do:
  continue it in the first terminal, or close or switch it there and run
  `/session resume <name>` here again, or start a new session. Nothing either
  terminal wrote is overwritten. Sessions shared through the daemon (hosted
  sessions mirrored into a terminal) are not affected.
- `goodvibes help` is built from one command list: it lists `setup [status]`
  and `open`, completion offers `subscription refresh` and `models chain`, and
  `serve` is gone from completion. `goodvibes setup status` is named where the
  doctor used to point elsewhere.
- `goodvibes plugin bundles install` takes `--sha256`; `--sha` and
  `--override` are gone.
- Auth failures name real commands: "Run /provider sign-in to sign in again
  (then /provider finish if it asks for a code)." for an ended subscription,
  and "Run /accounts repair to see what is wrong with the provider's account
  and fix it." for a refused key. There is no `/login` to point at.
- A project `VIBE.md` that resolves outside the project (git root, else the
  working directory) is not read. Global ones and a path you name are read as
  before.

## The Agent

- **`/plugin` and `/hooks`.** The Agent has the terminal app's `/plugin` (no
  `/plugin-trust`) and `/hooks`; `/hooks open` is refused in the Agent, saying
  "/hooks contracts lists the same".
- **Exit.** An exit after a clean save no longer says shutdown did not finish.
- **An inbound message whose hand-off answer was lost** is not run twice in the
  hosted session.
- **`/update`** lists no review actions (they exist only where the installer
  allows them), and adds `Daemon restart: ...` when the update replaced the
  daemon and its service is running.
- Update advice names the installer, never `bun add -g @goodvibes/agent`. A
  missing browser host script says to re-run the installer.
- `/network-scan on` and `off` save first; when the choice cannot be saved
  they refuse ("Not changed: ... scanning stays <recorded>") and `on` starts no
  scan. An unreadable decision file means no scan at start and a warning; the
  file is no longer reset to off.
- The process list says when the records of processes detached in earlier
  sessions cannot be read, and a detached start says why it was not recorded.
- A draft send stopped before dispatch reads failed ("Nothing was sent") and
  can be sent again.
- The Agent's help, background-command report and surface descriptions say
  `F2` opens Your agents.

## Both terminal programs

- `/security` and trust bundles show the permission mode in force, and the
  chosen mode with the reason when they differ: `permission mode: <in force>
  (chosen <x>: <reason>)`.
- A theme change applies at once, whoever writes it. The terminal app's `auto`
  wording says it applies at once when the terminal reported its background,
  otherwise at the next launch.
- A resumed session whose saved model cannot be selected warns: "The saved
  model X could not be selected here (reason); this session continues on Y."
- Unknown and failed commands read the same in both programs: "Unknown
  command: /x. Type /help for available commands." and "Command /x failed:
  <reason>".
- Key-action descriptions no longer name keys.
- `/notify remove` and `/notify clear` name any stored key they could not
  delete, with `/secrets delete <key>`.
- A channel webhook is shown as scheme and host plus "(secret)" in hold
  reasons and results, never the full address.
- The decision-credential picker says when stored names could not be read; a
  typed name reads "Use <name> (not checked)".
- Wake turned on without usable models shows the stopped microphone chip with
  the reason.
- `/payments` repeat windows show amounts in their currency's real units
  (`¥5,000`, `KWD 1.234`).
- Costs use one precision everywhere (4 decimals under $1), with `~` on
  estimates.
- `/mail send` after a failed or unconfirmed send may be sent again: the
  terminal app reuses the message's id, so the daemon does not deliver it twice
  within ten minutes, and the Agent keeps the same Message-ID. An unconfirmed
  send reads "The send was not confirmed; it may have gone (<reason>)." with
  "Check the Sent folder" as the next step. A message confirmed sent is
  refused again unless `--again`, which sends a new copy.
- Identical refused Google sends show once in `/google waiting`.
- First-run browser sign-in says what went wrong instead of "cancelled": the
  provider refused it, the sign-in came back but the provider did not complete
  it, or the sign-in could not wait for the browser, each with "Press ⏎ to
  start again." A code can still be pasted.
- A browser that `xdg-open` starts in the foreground counts as opened, so the
  sign-in finishes by itself; "Your browser did not open" is no longer printed
  for it, and that browser is no longer tied to the terminal.
- Telegram cursor recovery failures carry their real reason.
- A learning rollback whose record cannot be read says so ("Rollback refused:
  <id> could not be read (<reason>); nothing was restored. Try again.").
- A damaged `connected-daemons.json` is set aside as `.corrupt-*` and the next
  connect or `/auth login daemon` refuses once, naming the copy and saving
  nothing; the attempt after that saves normally.
- `/remote artifacts` shows `unknown`, not `running`, for a task the store no
  longer holds.

## Web UI

- **Signing in with the whole link.** Pasting the full link `goodvibes pair`
  prints signs in, or offers the daemon it names, where it used to fail with
  "may have expired". The field reads "Paste the link or code goodvibes pair
  prints". Settings > Account takes a link the same way, and refuses a link for
  another daemon (naming both), a relay code or a password payload with a
  sentence saying so.
- **Pair a new device** under Settings > Paired devices: after you confirm the
  device's name it shows a link, a QR code and a one-time "Show the sign-in
  code once".
- **One sign-out.** Settings > Account > Sign out is the same sign-out as the
  account menu's: the relay pairing goes too, and a failure to end the daemon
  session shows on the sign-in page with Try again and Leave it.
- **Owner-approval notices** follow events instead of a 3-second poll. After a
  sign-out or a daemon change the notice says "This tab signed out or changed
  daemon while the change waited" instead of "cancelled".
- A setting changed in another tab, on another device or from the command line
  is read again at once.
- A Stop pressed before the turn's start arrives keeps the turn on stopping.
- Restart daemon shows "The daemon did not restart: <reason>" when the service
  manager refuses, and the daemon's own sentence on success.
- Approve in advance says "Nothing was approved" only for a definite refusal.
  Otherwise it says the purchase may have been approved, and that approving
  the same merchant, item and amount again returns that approval.
- A test push the push service refused shows "Test push failed" with the
  reason; a device the test pruned turns the switch off.
- The phone node says "Not approved yet" while a pairing waits, and gives the
  daemon's own "request pairing again" text for a rejected, expired or used
  request.
- The account menu's owner name follows a profile rename, and its Model line
  appears.
- "Can't reach the daemon" names the address it is trying and the
  `goodvibes-daemon status` and `goodvibes-daemon start-service` commands. The
  no-update-status text names re-running the installer.
- Costs read the same on every screen: 4 decimals under $1, `~` for
  estimates, "price unknown" when there is no price.
- The intake and execution journals read, list and confirm at any size.

## Approvals and permissions

- **An approved change is put in effect when it is approved.** An owner-approved
  loosening (a session's permission mode, a loosening settings change) is
  applied as part of the approval. If it cannot be applied, the approver gets
  "The approved change could not be put in effect (...). Nothing was decided:
  the ask is still waiting; answer it again, or deny it." (`APPROVED_NOT_APPLIED`).
  An approved change that tries to write an approval itself is refused at
  once, by name, and the ask stays open.
- **Answering another node's approval.** A claim or cancel relayed to another
  node whose first answer was lost is reported as applied, not refused. An
  answer with "always for this project" (or any remember tier) keeps the rule
  on the node that owns the ask; a rule that cannot be saved comes back as
  `REMEMBER_NOT_SAVED`. The `NODE_UNREACHABLE` text states the configured
  wait.
- **Wrapped deletions are owner-only.** A deletion run through `setsid`,
  `flock` (with or without `-c`), `watch`, `systemd-run`, `script -c`,
  `parallel`, `busybox` or `env -S`, or inside a shell script the command runs,
  is an owner-only ask, never Jev's to approve, and the ask says it cannot be
  undone. The same wrapped sends raise a new-recipient ask. Never-run rules see
  the same commands. A command nested more than six levels deep, or a script
  too large to read, counts as a deletion and is refused by a never-run rule.
  A compiled program is no longer read as a script (`/usr/bin/git status`).
- Decision-model failure next steps say "in Settings (...)" instead of
  "/settings open".
- A card refusal on Google Chat, Teams, Mattermost, iMessage, BlueBubbles,
  telephony and Home Assistant names the channel.

## Channels, mail, calendar and voice

- **A send that may have arrived is not sent again.** A channel reply that
  timed out on a surface that cannot drop a repeat (Slack, Telegram, ntfy and
  others) is reported undelivered with "The message to <surface> may have
  arrived: ..." and not repeated. Discord bot posts and webhook posts carry an
  identity, so their retries are dropped by the receiver.
- **An answer owed to a chat by a closed session is sent.** A closed session
  that still owes a channel answer stays loaded until it is sent, across
  restarts. After the upgrade, a closed session that owed one under 3.3.4 is
  found at the first start and its answer is sent.
- **Notifications** keep one identity across retries and resends (a Discord
  nonce, an `Idempotency-Key` header on webhooks). A resent notification stays
  in the failed list until its resend is delivered. Notifications waiting to
  retry when the program stops appear in `/notify failed` with "The program
  stopped while this notification waited to retry; it was not sent. Resend it
  from the failed list."
- **Inbound webhooks with no credential** answer `Webhook not configured: set
  <setting>`, and `/channels doctor` has an "Inbound webhook credential"
  check. Discord interactions verify with the stored `surfaces.discord.publicKey`
  instead of always answering 503.
- **Credentials are read one way.** A broken credential reference shows as
  unresolved in status, and the environment's account is no longer used in
  its place for status, sending, Telegram polling or notifications. Logging
  out of Slack, Discord or ntfy removes every stored credential of the
  account, including the webhook URL, public key and ntfy topics.
- **Google Calendar create** that carries a uid returns the event already made
  after a lost answer instead of adding a second one; without a uid it fails
  with `CALENDAR_OUTCOME_UNKNOWN` naming the event id.
- A calendar token refresh overtaken by a new sign-in says it was "connected
  again or disconnected while its token was refreshing".
- OpenAI transcription works with the default model, and the OpenAI realtime
  session returns its secret.

## Automation, check-ins and watchers

- **A run interrupted by a restart is not retried on its own.** It says
  "Interrupted by a restart before it finished. It may already have done part
  of its work, so it was not retried; run it again by hand if it still needs
  to run." A check-in whose note may already have been sent is not retried
  either, and a run whose agent stopped without reporting says so.
- **A due run starts as soon as a slot frees**, not up to 15 seconds later.
- **Failure notices reach you.** A failed run's notice goes to the owner inbox
  when every target failed or delivery is off. A run answer that reached no
  inbox shows `not delivered` instead of `sent to your inbox` and stays owed
  until the next start.
- Enabling an expired one-shot, by toggle or by edit, leaves it disabled with
  `schedule-expired`. Enabling an archived job is refused (`INVALID_ARGUMENT`).
  Re-enabling a job paused for failures resets its failure count. A finished
  one-shot emits a job-updated event.
- **The check-in job belongs to `checkin.config.set`.** Removing, toggling or
  rescheduling it from `/schedule` or the operator API is refused, naming
  `checkin.config.set`; renaming it is allowed. `checkin.config.get` reports
  `failed` with a reason when the job is missing or out of step.
- **A watcher whose run fails** shows `degraded` with the error and keeps
  running on its interval, after a daemon restart too. `failed` now means
  nothing drives it.
- A knowledge refresh in which every source failed shows as failed with the
  first reason, instead of "completed, refreshed: 0". Accepting a
  source-refresh candidate gives the real reason.
- A workflow left without a move for an hour shows as cancelled, then is
  removed.

## Plugins, MCP and tools

- `/plugin enable` on a plugin that is enabled but not running starts it; on a
  running one it says it "is already enabled and running". A failed start says
  the plugin "stays enabled" or "was left disabled", or that the change could
  not be saved.
- A quarantine, enable or publisher key set in one window is not undone by
  another window, and shows in the other window's `/plugin list` at once.
- A plugin manifest with a top-level `hooks` field logs one warning: "hooks is
  not read; subscribe with api.onEvent and declare register.hook in
  capabilities".
- A trust mode or role set this session for an MCP server ends when a reload
  puts a different program behind that name. An MCP server that exits on its
  own is no longer restarted by the client; it is reported as given up.
- Pins and recent models made in one window show in another window's picker.
- A custom provider at a `*.ts.net` host keeps its own context window.
- The analyze tool lists `unreadable_files` for dependencies and env_audit and
  refuses impact on an unreadable target. AST edits work on `.mts`, `.cts` and
  `.htm`. A relative path in `remote import-artifact` is read from the project
  directory. The registry tool lists skills as the session loads them.
- Card material, snapshots and page grants are dropped when the browser or a
  tab closes or the browser crashes.
- A hunk revert or preview of a file under `.goodvibes/verification` is
  refused as a conflict.

## Devices, pairing and relay

- **A device whose pairing-verify answer was lost** can verify again with the
  same challenge, before the request expires and while the first token is
  unused, and gets a new token; the unused one is revoked. Before, it got 410
  and had to pair again.
- A narrowed device calling `pairing.handoff.create` is offered nothing (it
  gets its token alone); before, it was offered notifications and relay it
  could not complete.
- Minting a relay code no longer counts codes revoked with their device toward
  the 64-code cap.
- A peer token rotate or revoke that cannot be written to the shared authority
  record fails with nothing changed locally. A token revoked locally is never
  brought back by the authority record.
- Remote work that expires after its peer was removed still posts its note to
  the session and approval, and settles its run as failed with the expiry
  error.

## Installing and updating

- **The release installer exits 4** with "Installed, with the problems above."
  when the daemon service was not set up or is not running, the daemon restart
  did not happen, the web UI was not configured, or the no-service choice was
  not saved; each has a `NOT ...` line with the command that fixes it. The
  summary's `Web UI:` line gives the address only; the daemon's own lines above
  it say who can reach it. `docs/exit-codes.md` has the installer's codes.
- **An upgrade keeps a service you removed removed.** With no `--service` or
  `--no-service` given, the installer reads `service.enabled`, and when it is
  false prints `Daemon service: off by your choice (service.enabled is false),
  so none was set up.`
- A hand-started daemon is waited for until it exits, and `restarted` appears
  only once the new daemon is serving (on systemd, once the unit is
  `active`); otherwise a NOTE gives the command to run it in a terminal.
- Uninstall says when it could not check for a daemon service, and lists it
  under Preserved. Leftover install claim folders are removed, or named with
  how to finish them.
- `--decision-policy` with a bad value is checked by the daemon's `config set`,
  which lists the allowed values; the install finishes with `Decision policy:
  NOT saved`. `INSTALL_E111` is gone.
- **The checkout installer** keeps the owner's port, LAN posture and service
  choice on an update, manages the unit the daemon names, puts back the
  settings an interrupted update wrote, and reports a failing set decision
  model as a failure (exit 1) instead of "No decision model selected".
- The "outcome not known" settings error names `goodvibes-daemon config get
  <key>`, and for a daemon on another machine says where to run it.
- `push.vapidSubject` is shown as taking effect at restart.

## Stored data

Everything 3.3.4 wrote is read by 3.4.0; nothing needs converting.

- **Approval log** (`approvals.jsonl`): an audit entry may carry
  `relayRequestId`. Entries without it read as before.
- **Session index** (`sessions.json`, still version 2): a closed session's
  entry may carry `owedReplyCount`, and the index carries `owedReplyCounted`.
  An index 3.3.4 wrote has neither: at the first start, each closed session's
  log is read once for the channel answers 3.3.4 marked as owed, a session
  that owes one is loaded and its answer sent, the count is noted among what
  was carried forward, and the index is rewritten so later starts read
  nothing extra.
- **Sessions folder:** each session opened for writing has a
  `<name>.jsonl.held` lock file (empty). Listings read only `.jsonl` names,
  and deleting a session removes its `.held` file.
- **Distributed runtime state:** pair requests may carry `verifiedTokenId`. A
  request 3.3.4 stored has none, so its verify is not answered again.
  `metadata.bridgePending` is now set on every settled work record that owes a
  delivery until it is delivered; a 3.3.4 record without it owes nothing.
- **Remote execution artifacts:** `task.status` may be `unknown`; older files
  read unchanged.
- **`connected-daemons.json`:** same format; a file that is not a valid
  version 1 record is set aside as `.corrupt-*`, and a
  `connected-daemons.json.writer.sqlite` lock file sits beside it.
- **`plugins.json`:** same format; writes take a `plugins.json.writer.sqlite`
  lock, created at the first write.
- **Watcher records:** same format. A watcher 3.3.4 saved as `failed` stays
  stopped until it is started again.
- **Knowledge job runs:** runs may carry `owner.locked`, and refresh results
  may carry `attempted`, `failed` and `failures`. Runs without `locked` are
  settled by the old process-and-six-hours rule. Per-instance lock files
  (`<store>.run-owner.<instance>`) sit beside the knowledge store while it is
  open.
- **Trust bundles:** still version 1, with optional `permissionModeChosen` and
  `permissionModeReason`.
- **Automation runs:** a run may be saved with delivery attempts and still owe
  its answer; a deferred occurrence no longer moves the stored `nextRunAt`.
- **Checkout installer receipt** (`installation.json`): may carry
  `serviceName` (absent means `goodvibes`, the only name 3.3.4 used) and,
  only during an update, `pendingSettings`.
- **Daemon routines** created by `/schedule add` carry an id the terminal
  chose (`routine-<uuid>`).
- Unchanged in shape: notification dead letters (new rows are written at
  shutdown), the LAN-scan consent file (now written atomically), drafts, the
  detached-process records and the relay codes file (codes revoked on the
  authority record are pruned at the next mint).

## For client authors

The full reference is `docs/llms/70-api.md` (and `docs/llms-full.txt`).

- **Removed error code:** `TOKEN_EXPIRED`. It was never sent; an expired
  credential is answered `AUTH_REQUIRED`.
- **New error codes and answers:**
  - `GRANT_NOT_FOUND` (404, field `grantId`) from `devices.grants.revoke` for an
    unknown grant; the same call with no `grantId`, `nodeId` or `capabilityId`
    is `400` `INVALID_ARGUMENT`. Revoking an already revoked grant is safe to
    repeat. The Agent's phone tool gets the same error.
  - `APPROVED_NOT_APPLIED`, and a relayed action's broker error comes back with
    its own code and status (`REMEMBER_NOT_SAVED`, `APPROVED_NOT_APPLIED`,
    `INVALID_ARGUMENT`) instead of `NOT_APPLIED`/400.
  - `IDEMPOTENCY_OUTCOME_UNKNOWN` at `500` "failed partway" for a repeat of a
    keyed request whose first attempt threw; the `409` form is now only for a
    first attempt the daemon stopped in the middle of.
  - `CALENDAR_OUTCOME_UNKNOWN` (502) from a Google Calendar create whose answer
    was lost.
  - `RESULT_UNREADABLE` as `error.code` on a completed batch job whose result
    file cannot be read. `BATCH_DISABLED` reads "This daemon does not queue
    batch work: batch.mode is off." and carries `state` and `next`.
  - `APPROVAL_WRITE_IN_APPROVED_CHANGE`, the cause carried by
    `APPROVED_NOT_APPLIED` when an approved change's handler tried to write an
    approval; it names the handler and the approval.
  - `SESSION_OPEN_ELSEWHERE` from opening, saving or deleting a session that
    another terminal has open.
- **Changed answers:**
  - `pair.verify` answers again, with a new token, for a repeat with the same
    challenge before expiry while the first token is unused.
  - `pairing.handoff.create` offers only what the new pairing can complete.
  - The knowledge refresh job result gains optional `attempted`, `failed` and
    `failures`; a job that refreshed nothing because every source failed
    fails.
  - The approval audit entry gains optional `relayRequestId`.
  - Automation: enabling an archived job, and changing the check-in job other
    than by `checkin.config.set`, are `400` `INVALID_ARGUMENT`.
- **The exported daemon HTTP transport's approval actions** take
  `(approvalId, input)` with `expectedRevision`, no longer send `actor` or
  `actorSurface`, and return the whole outcome (`applied`, `approval`,
  `reading`, `refusal`, `recorded`), or null on a 404.
- **The Agent's daemon calls** send `x-goodvibes-client: agent`, and its
  hosted hand-off sends `Idempotency-Key: agent-handoff:<session>:<input>` on
  create and `messageId: agent-handoff:<input>` on each steer.
- Under `NODE_ENV=development`, going over the event listener cap logs a
  warning instead of throwing.
