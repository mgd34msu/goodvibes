# GoodVibes 3.4.0

GoodVibes 3.4.0 is about saying what really happened. Where a step could not
be finished, a send may already have gone, or a file could not be read, the
programs now say so with the reason and the next step, instead of reporting
success, retrying on their own, or quietly starting over. Where an answer was
lost, a repeat finds the first result instead of acting twice.

It also brings the Agent level with the terminal app on daemons elsewhere: it
dials the address you give it, https included, pairs and unpairs its host
from `/devices`, and has `/plugin` and `/hooks`. A session is written by one
terminal at a time, and `--force` hands it over instead of writing it twice.
The webhook listener has its own token. Contract gates, the exec tool and
sandbox sessions share one view of your home folder.

## Upgrading from 3.3.x

What you must do, or will notice, on the first start of 3.4.0.

**Do before or right after updating**

- **Webhook senders switch to the listener token.** The webhook listener no
  longer accepts the daemon's operator token, with no grace period. It has its
  own token, kept in `<daemon home>/http-listener-token.json` (or
  `GOODVIBES_HTTP_TOKEN` when set); `goodvibes-daemon listener token --show`
  prints it on that machine. Change every sender that posted to the listener
  with the operator token. See [The webhook listener](#the-webhook-listener).
- **Update the daemon before the terminal programs.** Both `goodvibes` and
  `goodvibes-agent` refuse a daemon older than 3.3.2 (it was 3.1.2): they call
  `inbox.answer`, `mcp.servers.reload`, the MCP trust, role, quarantine and
  tool-block methods, `relay.codes.*` and `automation.schedules.pause`,
  `resume` and `preview`, which an older daemon does not serve.
- **An Agent pointed at another machine by `controlPlane.host` alone** must have
  `daemon.connectedHost.url` set to that daemon's origin (`https://...`
  encrypted, or `http://...` to send the Agent's credentials unencrypted).
  Until then the Agent refuses before anything is sent, and the refusal gives
  the value to set. `/setup connect-daemon` writes it.
- **A corrupt `daemon-settings.json` now stops the daemon from starting.** The
  error names the file: `<path> could not be read (<cause>); fix or remove it,
  or start with --working-dir`. 3.3.4 ignored such a file.

**What the first start does by itself, and says once**

- Creates the webhook listener's token (when the listener is on and
  `GOODVIBES_HTTP_TOKEN` is not set) and says so once on the next terminal or
  web UI connect: "The webhook listener now has its own token and no longer
  accepts the operator token: every webhook sender must send the listener
  token instead. It is kept in <path>; on this machine, goodvibes-daemon
  listener token --show prints it."
- Moves `power.keepAwake` (keep-awake) from a terminal program's own settings
  into the daemon's settings, or drops it there when the daemon already sets
  it, and says so once. The value in force does not change.
- Removes `daemon.connectedHost.*` from the daemon's own settings file where
  3.3.4 copied it there, and says so once.
- Clears a stored `web.publicBaseUrl` that only held the daemon's own address,
  a loopback address or the old placeholder (`http://127.0.0.1:3423`), and
  prints one line. Links then follow the bind settings. An address you set by
  hand (a tunnel, a proxy) is kept.
- Finds the closed sessions that still owed a chat channel an answer under
  3.3.4, and sends those answers.
- Starts agreed work that 3.3.4 had accepted and not started, or tells the
  owner on its channel why it could not.

**Settings that moved or went away**

- `power.keepAwake` is the daemon's setting (moved, above).
- `push.subscriptions.sweepIntervalMinutes` is removed. A value left in a
  settings file is kept and reported as an unknown key; nothing reads it.
- `memory.projection.dir` is an ordinary setting shown under Memory (it was
  under Storage), with the same default and path. A stored empty value now
  reads as the default, with the usual notice.
- The notification, budget and code-index settings of the terminal app are
  checked like every other setting: a hand-edited `"false"` (text) reads as
  the default with a notice, instead of being reported as unknown.
- New: `webSearch.defaultProvider` (default `auto`, today's behaviour).

**Commands, codes and exit codes that changed**

- The Agent's `/plugin-trust` is `/plugin`, as in the terminal app.
- `/session resume <id> --force` no longer writes a session alongside the
  terminal that has it open; it asks that terminal to save and let go (see
  [Sessions open in two terminals](#sessions-open-in-two-terminals)).
- `/permissions add never ...` is refused with a pointer to `/permissions
  never <command>`.
- `goodvibes-daemon start-service` and `restart-service` exit `3` (was `0`)
  when the service is not running afterwards; `stop-service` exits `1` when it
  still runs; `uninstall-service` exits `1` and removes nothing when it cannot
  save the choice. The release installer can exit `4` ("installed, with
  problems"). The terminal app exits `143` on SIGTERM and `129` on SIGHUP.
- Removed error codes, and what is sent instead: `TOKEN_EXPIRED` (never sent;
  an expired credential is `AUTH_REQUIRED`); `VALIDATION_FAILED`,
  `INVALID_INPUT` and `INVALID_REQUEST` (all `INVALID_ARGUMENT`);
  `REQUIRE_CONFIRM` and `EXPLICIT_USER_REQUEST_REQUIRED` (both
  `CONFIRMATION_REQUIRED`); `step-up-required`, `relay-disabled` and
  `relay-code-revoked` (now `STEP_UP_REQUIRED`, `RELAY_DISABLED`,
  `RELAY_CODE_REVOKED`); the calendar's `UNAUTHENTICATED` at 401 (now
  `CALENDAR_AUTH_FAILED` at 424); `INSTALL_E111` (the daemon's `config set`
  checks the decision policy). Removed method: `knowledge.graphql.execute`
  (now `knowledge.graphql.query` and `knowledge.graphql.mutate`). Removed
  event: `COMPANION_MESSAGE_RECEIVED`. See [For client
  authors](#for-client-authors).

## Connecting to a daemon on another computer

- **`/setup connect-daemon`** ("Use a daemon on another computer") is a new
  setup topic in both programs. It points the program at a daemon already
  running elsewhere and opens nothing on this computer to the network. The
  `browser` and `other-devices` topics no longer show the daemon-source rows.
  Every message that used to say "/setup, Network step" now names `/setup
  connect-daemon`, and so does `/accounts sign-in daemon`.
- **The Agent dials one address.** It uses `daemon.connectedHost.url` when set,
  with its scheme, else this machine's daemon, over https when that daemon's
  TLS is on. Next steps that told you to fix `controlPlane.host` or
  `controlPlane.port` now name `daemon.connectedHost.url`.
- **`--runtime-url` and `GOODVIBES_AGENT_RUNTIME_URL` accept `https://`** and
  set `daemon.connectedHost.url` for that one run.
- **Pairing the Agent with a host.** A preview of an interrupted pairing to
  another machine never sends this machine's daemon token; it offers to forget
  the attempt and says why it was not repeated. A pairing cancelled before it
  was sent leaves nothing behind.
- **The Agent's `/devices`** now pairs, shows and unpairs its host (`pair
  host`, `host-status`, `unpair-host`) and handles the relay (pair, status,
  codes, revoke), the same flows as `/setup pair` and `/setup unpair`.
- A record the host does not have (a 404 naming a missing session or item)
  reads as "no such record" with the host's own next step, instead of "this
  command is not wired up" or "the host runs a different version", in both
  programs.
- Daemon refusals read by the cluster and status commands show the daemon's
  own next step.
- The live verifier finds the daemon's real port and scheme from the daemon's
  own settings.
- Endpoint displays show the normalized host mode (`Network` shows as
  `network`). An unrecognized `httpListener` or `web` host mode reads as
  "read as local, this computer only (127.0.0.1:<port>)"; an unrecognized
  control-plane mode says the daemon does not start until it is corrected. The
  address shown for a daemon about to start follows the same bind rule
  (127.0.0.1 for `local`, even with a custom host left over).
- Approvals and credential writes made by the Agent are recorded as coming from
  the Agent, not the web UI.
- **Settings of a daemon on another machine.** A program attached to a daemon
  elsewhere shows that daemon's settings and never reads or writes this
  machine's daemon settings file. A change while that daemon is down is
  refused: "<key> was not changed: the daemon at <origin> is not reachable,
  and its settings are kept on that machine, so nothing was changed. Try again
  once it answers."
- **This machine's daemon token stays on this machine.** The Agent sends
  `GOODVIBES_DAEMON_TOKEN` only to this machine's daemon, and
  `goodvibes-daemon pair` without `--host` only ever reaches this machine's
  daemon (from its bind settings, never `daemon.connectedHost.url`).
  `goodvibes-daemon pair --host http://127.0.0.1:3421` (or `localhost`,
  `[::1]`) reprints this machine's link instead of minting a device token.
- **A daemon that is still starting** is not reported as failed. Both programs
  print "[Startup] The GoodVibes daemon is starting; shared sessions, the web
  UI, phone access and the other things that need it work once it is ready.",
  carry on, and connect when the daemon's ready record says it is serving.
  The failure line appears only when the service has stopped.
- A daemon on another machine that has no stored credential shows as
  `blocked`, with the reason and next steps; it is never started from here.
- `/questions` and `/decisions` say when the daemon did not answer: "The
  daemon at <address> did not answer (<reason>); showing only what is held on
  this machine, so its approvals and questions are missing."

## Sessions open in two terminals

- **A session is written by one terminal at a time**, in both programs. A
  session open in one terminal cannot be resumed, saved or deleted from a
  second; the second is refused at resume (`SESSION_OPEN_ELSEWHERE`) before
  anything is read: "Continue it there, or run `/session resume <id> --force`
  to have that terminal save it and hand it over to this one." Nothing either
  terminal wrote is overwritten. Sessions shared through the daemon (hosted
  sessions mirrored into a terminal) are not affected.
- **`--force` hands the session over.** `/session resume <id> --force` asks the
  terminal that has the session open, through the daemon both are attached
  to, to save it and let go; it then resumes it here, and the other terminal
  says the session moved. Two terminals not attached to one daemon cannot
  reach each other: close the session in the other terminal first.
- **A chat message's sender is answered exactly once**, whoever runs the turn:
  the terminal running the session, the Agent's connected host, or the daemon.
  A message that failed before its turn started, or was still held when the
  program closed, is answered with that failure. Companion and ntfy chat
  messages are answered by the terminal running the session, and ntfy gets the
  reply on its topic.

## The terminal app

- **Starting on a session.** A `--resume`, `--continue` or `--fork` that cannot
  open its session prints `[Resume] Could not resume session <id>: <reason>`
  (`resume and fork` for `--fork`) and the app starts as a plain launch. Bare
  `--fork` now resumes the last session of the folder (the one `--continue`
  opens) and then forks it; nothing is forked when the resume fails.
- **Closing the window or sending SIGTERM** stops running `!` commands, `/test`
  runs and task processes, and the app exits 143 (SIGTERM) or 129 (SIGHUP).
- **A message sent while a `!` command runs** shows "Waiting for `!<cmd>` to
  finish ...; Esc stops it." and goes with that command's output, in order.
  This holds for typed and spoken messages, in both programs.
- An ask cancelled or answered elsewhere leaves the approval queue.
- `/test` started while a stopped run is still finishing is refused: "A test
  run is still going, or still finishing after a stop; Esc stops it, then run
  /test again once it has ended."
- `/session save-file` and upload no longer claim an upload or a copy that did
  not happen: the line says `(not uploaded)` or `(upload unconfirmed)`, and
  `(could not copy the path)` when the clipboard refused.
- `/schedule add` whose answer was lost does not create a second routine:
  "It may have been created; /schedule list shows it. Running the same line
  again will not create a second one."
- `goodvibes help` is built from one command list: it lists `setup [status]`
  and `open`, completion offers `subscription refresh` and `models chain`, and
  `serve` is gone from completion. `goodvibes setup status` is named where the
  doctor used to point elsewhere.
- `goodvibes plugin bundles install` takes `--sha256`; `--sha` and
  `--override` are gone.
- Auth failures name real commands: "Run /provider sign-in to sign in again
  (then /provider finish if it asks for a code)." for an ended subscription,
  and "Run /accounts repair to see what is wrong with the provider's account
  and fix it." for a refused key. There is no `/login` to point at.
- A project `VIBE.md` that resolves outside the project (git root, else the
  working directory) is not read. Global ones and a path you name are read as
  before.
- `/eval` stops on Esc and prints `[eval] Stopped; no result.`; a second eval
  while one runs is refused.
- `/template save` replies `Template replaced` when it overwrote one, takes
  `--everywhere`, refuses a name with nothing that can be stored, and stores
  `my.plan` as `myplan`. Template files whose name is not their stored name are
  no longer listed; the log names them.
- `/devices relay-status` shows `failed` with the reason when the relay could
  not start; changing `relay.url`, `relay.enabled` or the relay feature takes
  effect without a restart.

## The Agent

- **`/plugin` and `/hooks`.** The Agent has the terminal app's `/plugin` (no
  `/plugin-trust`) and `/hooks`; `/hooks open` is refused in the Agent, saying
  "/hooks contracts lists the same".
- **Exit.** An exit after a clean save no longer says shutdown did not finish.
- **An inbound message whose hand-off answer was lost** is not run twice in the
  hosted session.
- **`/update`** lists no review actions (they exist only where the installer
  allows them), and adds `Daemon restart: ...` when the update replaced the
  daemon and its service is running.
- Update advice names the installer, never `bun add -g @goodvibes/agent`. A
  missing browser host script says to re-run the installer.
- `/network-scan on` and `off` save first; when the choice cannot be saved
  they refuse ("Not changed: ... scanning stays <recorded>") and `on` starts no
  scan. An unreadable decision file means no scan at start and a warning; the
  file is no longer reset to off.
- The process list says when the records of processes detached in earlier
  sessions cannot be read, and a detached start says why it was not recorded.
- A draft send stopped before dispatch reads failed ("Nothing was sent") and
  can be sent again.
- The Agent's help, background-command report and surface descriptions say
  `F2` opens Your agents.

- `/security` and trust bundles show the permission mode in force, and the

  (chosen <x>: <reason>)`.
- A theme change applies at once, whoever writes it. The terminal app's `auto`

- The decision-credential picker says when stored names could not be read; a

- Telegram cursor recovery failures carry their real reason.
- A learning rollback whose record cannot be read says so ("Rollback refused:
  <id> could not be read (<reason>); nothing was restored. Try again.").
- A damaged `connected-daemons.json` is set aside as `.corrupt-*` and the next
  connect or `/auth login daemon` refuses once, naming the copy and saving

- `/remote artifacts` shows `unknown`, not `running`, for a task the store no

- **The settings screens** show each setting's default as the program's own
  default, and "reset to" names it; in the Agent, reset removes the stored
  value instead of writing the default. The memory files folder

- `/plugin list`, `/plugin capabilities` and the plugins screen say when a

- Restricting a folder stops its hooks and MCP servers at once, and the reply
  says so.
- An MCP server that refuses its credentials waits in `auth_required` and is not

- The Agent's model can no longer claim approvals or cancel asks it did not

## Approvals and permissions

- **An approved change is put in effect when it is approved.** An owner-approved
  loosening (a session's permission mode, a loosening settings change) is
  applied as part of the approval. If it cannot be applied, the approver gets
  "The approved change could not be put in effect (...). Nothing was decided:
  the ask is still waiting; answer it again, or deny it." (`APPROVED_NOT_APPLIED`).
  An approved change that tries to write an approval itself is refused at
  once, by name, and the ask stays open.
- **Answering another node's approval.** A claim or cancel relayed to another
  node whose first answer was lost is reported as applied, not refused. An
  answer with "always for this project" (or any remember tier) keeps the rule
  on the node that owns the ask; a rule that cannot be saved comes back as
  `REMEMBER_NOT_SAVED`. The `NODE_UNREACHABLE` text states the configured
  wait.
- **Wrapped deletions are owner-only.** A deletion run through `setsid`,
  `flock` (with or without `-c`), `watch`, `systemd-run`, `script -c`,
  `parallel`, `busybox` or `env -S`, or inside a shell script the command runs,
  is an owner-only ask, never Jev's to approve, and the ask says it cannot be
  undone. The same wrapped sends raise a new-recipient ask. Never-run rules see
  the same commands. A command nested more than six levels deep, or a script
  too large to read, counts as a deletion and is refused by a never-run rule.
  A compiled program is no longer read as a script (`/usr/bin/git status`).
- **One confirmation rule.** Every method that needs a confirmation, the
  owner's own request or a request not declined is checked the same way before
  it runs, on every path, and every such refusal is `CONFIRMATION_REQUIRED`
  saying which fact was missing (`400` when `confirm` is missing, `403` when it
  was declined or came on a credential that cannot say a person asked).
- **Who may revoke a device.** Revoking a device token you did not hold or mint
  is the owner's; an admin's request is put to the owner (`202`
  `OWNER_APPROVAL_PENDING`), anyone else is refused `OWNER_ONLY`. Revoking the
  shared operator token is the owner's alone.
- **Hosted sessions are their owners'.** Paired devices and members no longer
  see, list, search or control other principals' hosted sessions (`403`
  `NOT_YOURS`).
- **Over the relay, a write needs a passkey by what it does.** Step-up reads the
  method's effect, so a read sent by POST is not gated and a write is.
  Knowledge GraphQL mutations go to their own route and need the passkey.
- Decision-model failure next steps say "in Settings (...)" instead of
  "/settings open".
- A card refusal on Google Chat, Teams, Mattermost, iMessage, BlueBubbles,
  telephony and Home Assistant names the channel.

## Channels, mail, calendar and voice

- **A send that may have arrived is not sent again.** A channel reply that
  timed out on a surface that cannot drop a repeat (Slack, Telegram, ntfy and
  others) is reported undelivered with "The message to <surface> may have
  arrived: ..." and not repeated. Discord bot posts and webhook posts carry an
  identity, so their retries are dropped by the receiver.
- **An answer owed to a chat by a closed session is sent.** A closed session
  that still owes a channel answer stays loaded until it is sent, across
  restarts. After the upgrade, a closed session that owed one under 3.3.4 is
  found at the first start and its answer is sent.
- **Notifications** keep one identity across retries and resends (a Discord
  nonce, an `Idempotency-Key` header on webhooks). A resent notification stays
  in the failed list until its resend is delivered. Notifications waiting to
  retry when the program stops appear in `/notify failed` with "The program
  stopped while this notification waited to retry; it was not sent. Resend it
  from the failed list."
- **Inbound webhooks with no credential** answer `Webhook not configured: set
  <setting>`, and `/channels doctor` has an "Inbound webhook credential"
  check. Discord interactions verify with the stored `surfaces.discord.publicKey`
  instead of always answering 503.
- **Credentials are read one way.** A broken credential reference shows as
  unresolved in status, and the environment's account is no longer used in
  its place for status, sending, Telegram polling or notifications. Logging
  out of Slack, Discord or ntfy removes every stored credential of the
  account, including the webhook URL, public key and ntfy topics.
- **Google Calendar create** that carries a uid returns the event already made
  after a lost answer instead of adding a second one; without a uid it fails
  with `CALENDAR_OUTCOME_UNKNOWN` naming the event id.
- A calendar token refresh overtaken by a new sign-in says it was "connected
  again or disconnected while its token was refreshing".
- OpenAI transcription works with the default model, and the OpenAI realtime
  session returns its secret.
- An emptied `surfaces.ntfy.baseUrl` means ntfy.sh for every publish, poll,
  subscribe URL and credential check, instead of failing.
- A post in a Telegram channel the bot was added to is a sender of its own
  (the channel), so it raises an owner claim naming the channel, is a guest, or
  is refused by policy; it never runs as the owner.
- Discord and ntfy approval prompts say how to reply: `Reply /approve <id> or
  /deny <id>.` without a decision model, otherwise `Reply yes or no, or say
  what to change.`
- Home Assistant is never used for owner alerts, approvals or mail notices.
  Its cancel answers what really happened to a known message (completed,
  cancelled, failed) or `not-running`.
- A refused mail or calendar password is answered `424`
  (`EMAIL_CREDENTIALS_REJECTED`, `CALENDAR_AUTH_FAILED`), so no client reads it
  as "signed out".
- `email.inbox.read` keeps a message whose body could not be fetched as read,
  with headers and `bodyUnavailable` naming the section and reason.

## Automation, check-ins and watchers

- **A run interrupted by a restart is not retried on its own.** It says
  "Interrupted by a restart before it finished. It may already have done part
  of its work, so it was not retried; run it again by hand if it still needs
  to run." A check-in whose note may already have been sent is not retried
  either, and a run whose agent stopped without reporting says so.
- **A due run starts as soon as a slot frees**, not up to 15 seconds later.
- **Failure notices reach you.** A failed run's notice goes to the owner inbox
  when every target failed or delivery is off. A run answer that reached no
  inbox shows `not delivered` instead of `sent to your inbox` and stays owed
  until the next start.
- Enabling an expired one-shot, by toggle or by edit, leaves it disabled with
  `schedule-expired`. Enabling an archived job is refused (`INVALID_ARGUMENT`).
  Re-enabling a job paused for failures resets its failure count. A finished
  one-shot emits a job-updated event.
- **The check-in job belongs to `checkin.config.set`.** Removing, toggling or
  rescheduling it from `/schedule` or the operator API is refused, naming
  `checkin.config.set`; renaming it is allowed. `checkin.config.get` reports
  `failed` with a reason when the job is missing or out of step.
- **A watcher whose run fails** shows `degraded` with the error and keeps
  running on its interval, after a daemon restart too. `failed` now means
  nothing drives it.
- A knowledge refresh in which every source failed shows as failed with the
  first reason, instead of "completed, refreshed: 0". Accepting a
  source-refresh candidate gives the real reason.
- A workflow left without a move for an hour shows as cancelled, then is
  removed.
- **Schedules use your time zone.** A cron schedule created without a zone
  follows `daemon.timezone` (or the zone in your profile), not the server's;
  schedule words name the zone when it differs from yours. Receipt times carry
  the zone's name.
- A message waiting for a free agent, and an orchestration item refused for
  capacity, start as soon as a slot frees.
- Work you agreed to over a chat that a restart interrupted is reported to you
  ("The agreed work was interrupted by a restart: <summary>. Send the message
  again.") instead of being run twice; agreed work that could not start is
  reported on your channel instead of vanishing.
- Contract gates run inside the sandbox, without credential variables in their
  environment; a gate that had to run on the host says so. A retried
  `contracts.dispatch` returns the same contract, after a restart too.

## Plugins, MCP and tools

- `/plugin enable` on a plugin that is enabled but not running starts it; on a
  running one it says it "is already enabled and running". A failed start says
  the plugin "stays enabled" or "was left disabled", or that the change could
  not be saved.
- A quarantine, enable or publisher key set in one window is not undone by
  another window, and shows in the other window's `/plugin list` at once.
- A plugin manifest with a top-level `hooks` field logs one warning: "hooks is
  not read; subscribe with api.onEvent and declare register.hook in
  capabilities".
- A trust mode or role set this session for an MCP server ends when a reload
  puts a different program behind that name. An MCP server that exits on its
  own is no longer restarted by the client; it is reported as given up.
- Pins and recent models made in one window show in another window's picker.
- A custom provider at a `*.ts.net` host keeps its own context window.
- The analyze tool lists `unreadable_files` for dependencies and env_audit and
  refuses impact on an unreadable target. AST edits work on `.mts`, `.cts` and
  `.htm`. A relative path in `remote import-artifact` is read from the project
  directory. The registry tool lists skills as the session loads them.
- Card material, snapshots and page grants are dropped when the browser or a
  tab closes or the browser crashes.
- A hunk revert or preview of a file under `.goodvibes/verification` is
  refused as a conflict.

## Devices, pairing and relay

- **A device whose pairing-verify answer was lost** can verify again with the
  same challenge, before the request expires and while the first token is
  unused, and gets a new token; the unused one is revoked. Before, it got 410
  and had to pair again.
- A narrowed device calling `pairing.handoff.create` is offered nothing (it
  gets its token alone); before, it was offered notifications and relay it
  could not complete.
- Minting a relay code no longer counts codes revoked with their device toward
  the 64-code cap.
- A peer token rotate or revoke that cannot be written to the shared authority
  record fails with nothing changed locally. A token revoked locally is never
  brought back by the authority record.
- Remote work that expires after its peer was removed still posts its note to
  the session and approval, and settles its run as failed with the expiry
  error.

## The webhook listener

- **It accepts only its own token.** The listener uses `GOODVIBES_HTTP_TOKEN`,
  else its own token file, `<daemon home>/http-listener-token.json` (mode
  0600), created on the first start with the listener on. It never accepts the
  daemon's operator token.
- **`goodvibes-daemon listener token [--show] [--json]`** says whether the
  listener is on, where its token comes from and the file's path; `--show`
  prints the token. It only reads, starts nothing and contacts no daemon;
  `--show` with no token exits `1` (`LISTENER_TOKEN_MISSING`).
- **A sender still on the operator token** is answered `401`
  `OPERATOR_TOKEN_NOT_ACCEPTED`: "The operator token is not accepted by the
  webhook listener. Send the listener token instead.", with the command and
  file name as the next step. The first such refusal in each daemon run puts
  one report in the owner inbox, "A webhook sender is still sending the
  operator token"; later ones in that run only answer the sender.
- The token is said once when it is created (see [Upgrading from
  3.3.x](#upgrading-from-33x)), and the interactive start line names the
  command.

## The daemon

- **Service commands report what is true afterwards.** `start-service` and
  `restart-service` exit `3` with `it is not running` when the service is not
  running afterwards; `stop-service` exits `1` with `service stop failed: ...
  is still running`. `goodvibes service start|restart|stop` passes these on.
- **`uninstall-service` saves your choice first.** It writes `service.enabled`
  and `service.autostart` off before removing anything; when it cannot, it
  refuses with exit `1` (`service uninstall refused: <reason>, so nothing was
  removed.`), naming a managed-policy lock or the settings file.
- **Every `--json` failure is a JSON document** on stdout: `{ok:false, code,
  error, fix}` with `COMMAND_REFUSED`, `PARSE_ERROR`, `COMMAND_FAILED`, the
  service codes `SERVICE_ACTION_FAILED`, `SERVICE_NOT_RUNNING`,
  `SERVICE_NOT_INSTALLED`, `SERVICE_DEFINITION_NOT_OURS`, or `WEBUI_REFUSED` /
  `WEBUI_FAILED`. `service-status --json` carries the schema
  `goodvibes.daemon.service-status` v1; `webui enable --json` prints its
  receipt, and `webui status --json` adds `serve` and `bundleDir`.
- **`web.publicBaseUrl` is never filled in by the daemon.** Empty means the
  address derived from the bind settings. `webui enable` never writes it;
  `webui disable` clears it when it held only this daemon's own address, and
  keeps a tunnel or proxy address, saying links still use it. `pair` then
  refuses with "no web UI is served" instead of printing a dead link.
- A page load with the web UI switched on and no bundle answers `503` with the
  setting that named the folder and the next step.
- `controlPlane.trustProxy`, `httpListener.trustProxy` and the listener's
  origin rules are read on every request. A request carrying the web UI's
  sign-in cookie must come from the daemon's own origins.
- `pair` names an HTTP error status ("the daemon at <url> answered HTTP
  <status>") instead of "no daemon answered".
- `mcp serve` offers only the methods the daemon serves, and refuses to start
  when it cannot read them.
- On the manual service platform the next step is `goodvibes-daemon
  start-service`, then `goodvibes-daemon service-status`.
- An owner alert kept as a receipt is shown only to the owner. A failed
  `service.autostart` check at start raises an owner alert.
- A daemon that ends within seconds of starting still writes its
  carried-forward line. A raw-prompt telemetry warning is logged when the
  setting is turned on at run time too.
- `storage.artifacts.maxBytes` and `network.remoteFetch.allowPrivateHosts`
  apply at the next upload or fetch, without a restart. A remote artifact or
  knowledge URL whose name resolves to a private or loopback address is
  refused (`DESTINATION_REFUSED`), naming the address.
- A malformed `goodvibes://secrets/` value in a credential setting is refused
  when written (`CONFIG_SECRET_REFERENCE_INVALID`), naming the shape
  `goodvibes://secrets/goodvibes/<KEY>`.
- A stop during a working-directory move no longer waits out the move's pause.
  When the saved working directory could not be put back, the reason says the
  next start goes to the failed folder and how to set it back.

## The sandbox and your home folder

Contract gates, the exec tool and sandbox sessions show your home folder the
same way:

- **Hidden:** `~/.goodvibes`, ssh and gpg keys, cloud, registry and token
  files (`.aws`, `.kube`, `.docker`, gcloud, gh, `.netrc`, `.npmrc`,
  `.pypirc`, cargo credentials and the like), browser profiles and caches, and
  shell history. A secret inside a shown folder is covered again.
- **Read-only:** toolchain installs and shims (rustup, cargo's `bin`, nvm,
  pyenv, asdf, mise, bun's `bin`, Go's `bin`, your git config, the `PATH`
  folders inside home).
- **Writable:** build caches (`~/.cache`, Go's build and module caches,
  cargo's registry, bun's, npm's, pnpm's, yarn's, pip's and uv's caches), so
  `go build`, `cargo build`, `bun install`, `npm ci` and `pip install` work
  with no setting.
- A write refused in a toolchain folder, or a path home hides, gets a sentence
  saying why and naming `sandbox.workspaceWritable`, the setting that shows a
  path (writable).

## Installing and updating

- **Asking the daemon to check for an update answers at once.** When the check
  finds a release and the handover is reserved, the answer is `check: found
  <version>; the daemon is installing it now and will restart into it`, with a
  line saying it stops answering for a short while. Before, the client waited
  and then reported that the daemon could not be reached.
- **After a restart accepted by systemd, the old daemon exits at once** instead
  of using a full processor core until it was stopped.
- The installer's summary says how to sign in: "Sign in: run goodvibes pair (or
  goodvibes-daemon pair) and open the link it prints, or scan its QR". An
  installer run no longer turns a web UI you switched off back on ("Web UI:
  left off (you turned it off). Turn it on: goodvibes-daemon webui enable").
- Uninstalling without a receipt fetches the uninstaller of the installed
  daemon's version, not `main`, and says so when it cannot tell.
- **The release installer exits 4** with "Installed, with the problems above."
  when the daemon service was not set up or is not running, the daemon restart
  did not happen, the web UI was not configured, or the no-service choice was
  not saved; each has a `NOT ...` line with the command that fixes it. The
  summary's `Web UI:` line gives the address only; the daemon's own lines above
  it say who can reach it. `docs/exit-codes.md` has the installer's codes.
- **An upgrade keeps a service you removed removed.** With no `--service` or
  `--no-service` given, the installer reads `service.enabled`, and when it is
  false prints `Daemon service: off by your choice (service.enabled is false),
  so none was set up.`
- A hand-started daemon is waited for until it exits, and `restarted` appears
  only once the new daemon is serving (on systemd, once the unit is
  `active`); otherwise a NOTE gives the command to run it in a terminal.
- Uninstall says when it could not check for a daemon service, and lists it
  under Preserved. Leftover install claim folders are removed, or named with
  how to finish them.
- `--decision-policy` with a bad value is checked by the daemon's `config set`,
  which lists the allowed values; the install finishes with `Decision policy:
  NOT saved`. `INSTALL_E111` is gone.
- **The checkout installer** keeps the owner's port, LAN posture and service
  choice on an update, manages the unit the daemon names, puts back the
  settings an interrupted update wrote, and reports a failing set decision
  model as a failure (exit 1) instead of "No decision model selected".
- The "outcome not known" settings error names `goodvibes-daemon config get
  <key>`, and for a daemon on another machine says where to run it.
- `push.vapidSubject` is shown as taking effect at restart.

## Stored data

Everything 3.3.4 wrote is read by 3.4.0; nothing needs converting.

- **Approval log** (`approvals.jsonl`): an audit entry may carry
  `relayRequestId`. Entries without it read as before.
- **Session index** (`sessions.json`, still version 2): a closed session's
  entry may carry `owedReplyCount`, and the index carries `owedReplyCounted`.
  An index 3.3.4 wrote has neither: at the first start, each closed session's
  log is read once for the channel answers 3.3.4 marked as owed, a session
  that owes one is loaded and its answer sent, the count is noted among what
  was carried forward, and the index is rewritten so later starts read
  nothing extra.
- **Sessions folder:** each session opened for writing has a
  `<name>.jsonl.held` lock file (empty). Listings read only `.jsonl` names,
  and deleting a session removes its `.held` file.
- **Distributed runtime state:** pair requests may carry `verifiedTokenId`. A
  request 3.3.4 stored has none, so its verify is not answered again.
  `metadata.bridgePending` is now set on every settled work record that owes a
  delivery until it is delivered; a 3.3.4 record without it owes nothing.
- **Remote execution artifacts:** `task.status` may be `unknown`; older files
  read unchanged.
- **`connected-daemons.json`:** same format; a file that is not a valid
  version 1 record is set aside as `.corrupt-*`, and a
  `connected-daemons.json.writer.sqlite` lock file sits beside it.
- **`plugins.json`:** same format; writes take a `plugins.json.writer.sqlite`
  lock, created at the first write.
- **Watcher records:** same format. A watcher 3.3.4 saved as `failed` stays
  stopped until it is started again.
- **Knowledge job runs:** runs may carry `owner.locked`, and refresh results
  may carry `attempted`, `failed` and `failures`. Runs without `locked` are
  settled by the old process-and-six-hours rule. Per-instance lock files
  (`<store>.run-owner.<instance>`) sit beside the knowledge store while it is
  open.
- **Trust bundles:** still version 1, with optional `permissionModeChosen` and
  `permissionModeReason`.
- **Automation runs:** a run may be saved with delivery attempts and still owe
  its answer; a deferred occurrence no longer moves the stored `nextRunAt`.
- **Checkout installer receipt** (`installation.json`): may carry
  `serviceName` (absent means `goodvibes`, the only name 3.3.4 used) and,
  only during an update, `pendingSettings`.
- **Daemon routines** created by `/schedule add` carry an id the terminal
  chose (`routine-<uuid>`).
- **New file `<daemon home>/http-listener-token.json`** (the same record shape
  as `operator-tokens.json`), created on the first start with the listener on.
- **Daemon settings:** `power.keepAwake` is carried in from a terminal
  program's own settings file once; `daemon.connectedHost.*` copied there by
  3.3.4 is removed once; a `web.publicBaseUrl` that held the daemon's own,
  loopback or placeholder address is cleared once. Each says so once.
- **`daemon-receipts.json`:** an entry may carry `audience: 'owner'`; entries
  without it are shown to everyone, as before.
- **Work proposals:** an accepted record may carry `starting`. A 3.3.4 record
  without it reads as not claimed, and one accepted but not started is started
  once at the next start (or settled with a notice).
- **Contracts:** a record may carry `sessionCreatedForDispatch`; a gate result
  may carry `backend`. Retry keys for `contracts.dispatch` are kept as files in
  `<workspace>/.goodvibes/contracts/idempotency/` (3.3.4 kept them in memory
  only, so there is nothing to carry forward).
- **Idempotent-replay entries** may carry `headers`; entries 3.3.4 wrote replay
  without them.
- **New file `payments-order-mail-pending.json`** under the daemon's
  control-plane store: order mails waiting to be checked. An unreadable file is
  set aside and the list starts empty.
- **Push subscriptions:** a removal may carry the reason `access-withdrawn`.
- **Turn-anchor sidecars:** an unreadable one is set aside as
  `.corrupt-<time>` with a warning instead of being overwritten.
- **Settings, secrets and sign-ins** are written with a folder sync; their
  format is unchanged. A `daemon-settings.json` that is not valid JSON is now
  refused instead of ignored.
- **Templates** keep their names; an existing file name is its own stored name.
- Unchanged in shape: notification dead letters (new rows are written at
  shutdown), the LAN-scan consent file (now written atomically), drafts, the
  detached-process records and the relay codes file (codes revoked on the
  authority record are pruned at the next mint).

## For client authors

The full reference is `docs/llms/70-api.md` (and `docs/llms-full.txt`).

- **Removed error codes**, and what comes instead:
  - `TOKEN_EXPIRED`: it was never sent; an expired credential is answered
    `AUTH_REQUIRED`.
  - `VALIDATION_FAILED`, `INVALID_INPUT` and `INVALID_REQUEST`: every bad-input
    refusal is `INVALID_ARGUMENT` (status 400 and category `bad_request` read
    as it).
  - `REQUIRE_CONFIRM` and `EXPLICIT_USER_REQUEST_REQUIRED`:
    `CONFIRMATION_REQUIRED`, field `confirm`, with `state` and `next`. Method
    descriptors declare `confirmation` (`confirm`, `owner-request` or
    `not-declined`), and `confirm` is no longer in those methods' required
    input lists.
  - `step-up-required`, `relay-disabled`, `relay-code-revoked`: now
    `STEP_UP_REQUIRED` (a `401` with category `permission`, not
    authentication), `RELAY_DISABLED` and `RELAY_CODE_REVOKED`.
  - Calendar `UNAUTHENTICATED` at `401`: `CALENDAR_AUTH_FAILED` at `424`; mail
    `EMAIL_CREDENTIALS_REJECTED` is also `424`.
- **Removed and new methods:** `knowledge.graphql.execute` is split into
  `knowledge.graphql.query` (`POST`/`GET /api/knowledge/graphql`) and
  `knowledge.graphql.mutate` (`POST /api/knowledge/graphql/mutate`); each
  route refuses the other kind (`GRAPHQL_MUTATION_NOT_ALLOWED`,
  `GRAPHQL_QUERY_NOT_ALLOWED`). New: `sessions.hosted.unshare`; `remote.pair.requests.*`
  is now wrapped by the web UI and `/devices`. `sessions.hosted.share` refuses an
  unknown principal `404` `PRINCIPAL_NOT_FOUND`.
- **Removed event:** `COMPANION_MESSAGE_RECEIVED`.
- **`sessions.messages.create` with no `kind`** queues a follow-up turn and
  answers `202` `{messageId?, sessionId, inputId, mode}`; there is no
  `routedTo`.
- **`companion.chat.turns.cancel`** with no `turnId` cancels a turn that is on
  its way and answers `cancelled: true, stoppedBeforeStart: true` with
  `messageIds`; `NO_ACTIVE_TURN` only when nothing runs or is on its way.
- **Event streams over WebSocket:** event frames carry the record `id`; a new
  socket may pass `?lastEventId=` and is replayed from it, with `resume` in its
  `ready` frame. Unknown domains are named back (`unrecognisedDomains`) and a
  list with none known is refused `UNKNOWN_EVENT_DOMAIN`; withheld domains are
  named (`withheldDomains`). A `read:own-sessions` credential that also holds
  `read:approvals` gets every `approval-update`, and `OWNER_APPROVAL_PENDING`
  carries `followable`.
- **Idempotency:** `409` `IDEMPOTENCY_KEY_IN_FLIGHT` carries `Retry-After: 1`
  and the SDK retries it within its attempt budget; a replay keeps the first
  answer's `Retry-After` and `Location`; every SDK error carries the
  `idempotencyKey`. `email.draft.create`, `artifacts.create` and
  `companion.chat.sessions.create` take an `Idempotency-Key`;
  `payments.cards.create` returns the stored card for a repeat of the same
  card.
- **Route refusals** carry `state` and `next` as other refusals do. The
  descriptor's `ownerOnly` now means the least class is the owner;
  `modelRefused` says a model never calls the method.
- **Other new codes:** `OPERATOR_TOKEN_NOT_ACCEPTED` (`401` at the webhook
  listener), `CONFIG_SECRET_REFERENCE_INVALID`, `DESTINATION_REFUSED` for an
  artifact fetch, `403` `NOT_YOURS` for another principal's hosted session,
  `403` `OWNER_ONLY` for an agent credential claiming an approval or cancelling
  one it did not raise.
- `web_search.providers.list` returns `defaultProviderId`; a contract gate
  result carries `backend`; the relay status may be `failed` with
  `lastRefusal`.
- **New error codes and answers:**
  - `GRANT_NOT_FOUND` (404, field `grantId`) from `devices.grants.revoke` for an
    unknown grant; the same call with no `grantId`, `nodeId` or `capabilityId`
    is `400` `INVALID_ARGUMENT`. Revoking an already revoked grant is safe to
    repeat. The Agent's phone tool gets the same error.
  - `APPROVED_NOT_APPLIED`, and a relayed action's broker error comes back with
    its own code and status (`REMEMBER_NOT_SAVED`, `APPROVED_NOT_APPLIED`,
    `INVALID_ARGUMENT`) instead of `NOT_APPLIED`/400.
  - `IDEMPOTENCY_OUTCOME_UNKNOWN` at `500` "failed partway" for a repeat of a
    keyed request whose first attempt threw; the `409` form is now only for a
    first attempt the daemon stopped in the middle of.
  - `CALENDAR_OUTCOME_UNKNOWN` (502) from a Google Calendar create whose answer
    was lost.
  - `RESULT_UNREADABLE` as `error.code` on a completed batch job whose result
    file cannot be read. `BATCH_DISABLED` reads "This daemon does not queue
    batch work: batch.mode is off." and carries `state` and `next`.
  - `APPROVAL_WRITE_IN_APPROVED_CHANGE`, the cause carried by
    `APPROVED_NOT_APPLIED` when an approved change's handler tried to write an
    approval; it names the handler and the approval.
  - `SESSION_OPEN_ELSEWHERE` from opening, saving or deleting a session that
    another terminal has open.
- **Changed answers:**
  - `pair.verify` answers again, with a new token, for a repeat with the same
    challenge before expiry while the first token is unused.
  - `pairing.handoff.create` offers only what the new pairing can complete.
  - The knowledge refresh job result gains optional `attempted`, `failed` and
    `failures`; a job that refreshed nothing because every source failed
    fails.
  - The approval audit entry gains optional `relayRequestId`.
  - Automation: enabling an archived job, and changing the check-in job other
    than by `checkin.config.set`, are `400` `INVALID_ARGUMENT`.
- **The exported daemon HTTP transport's approval actions** take
  `(approvalId, input)` with `expectedRevision`, no longer send `actor` or
  `actorSurface`, and return the whole outcome (`applied`, `approval`,
  `reading`, `refusal`, `recorded`), or null on a 404.
- **The Agent's daemon calls** send `x-goodvibes-client: agent`, and its
  hosted hand-off sends `Idempotency-Key: agent-handoff:<session>:<input>` on
  create and `messageId: agent-handoff:<input>` on each steer.
- Under `NODE_ENV=development`, going over the event listener cap logs a
  warning instead of throwing.
