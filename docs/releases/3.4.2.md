# GoodVibes 3.4.2

GoodVibes 3.4.2 changes how an update downloads. A slow connection no longer
fails an update after two minutes, an update in progress shows how much has
arrived, and a release is no longer held in memory while it downloads. Nothing
you have stored changes.

## Upgrading

- **The update to 3.4.2 is done by the release you are running.** A 3.4.1 or
  earlier daemon still has its own two-minute limit, so on a slow connection it
  can stop part way through downloading 3.4.2. It tries again at its next check, and `goodvibes-daemon update --check` asks
  it to try at once. From 3.4.2 on, the limit is gone.

## Updates

- **No clock ends an update.** A slow download is not a failed update. The
  daemon's own update, `goodvibes update`, the Agent's `/update` and the
  Agent's hourly update run until the release has arrived and is installed,
  the release server or the connection fails, the update is cancelled, or the
  program stops. A transfer that receives nothing for 300 seconds is still
  ended.
- **`goodvibes-daemon update` and `/update daemon` show an update in
  progress:** `installing: <version>, downloading for <time>: <size> received
  (now <file>)`. After `--check` finds a release, it says to run the command
  again to see how much has downloaded.
- **The `pending:` line says only what is true.** A release that waits for the
  daemon to finish its work reads `pending: <version> was found (waiting
  <time>); it downloads and installs when no work is in flight` (or `when this
  work finishes: <id>, ...`). It no longer says the release was downloaded and
  verified, which it was not yet.
- **An update at start-up is no longer cancelled.** When `goodvibes` or
  `goodvibes-agent` starts and the update takes longer than
  `update.applyTimeoutMs` (default 45 seconds), the installed version starts
  and the download carries on in the background: `update still downloading in
  background; restart to use <new> once it completes`, then a line when it is
  installed or has failed. `update deferred: will retry next launch` is gone.
  The setting is now how long a launch waits, not how long an update may take.
- **Updates use far less memory.** Release files are written to disk as they
  arrive and checked in pieces, instead of being held in memory whole (an
  update had been peaking at about 2.7 GB). They go to a private folder beside
  the installation, `.update-fetch-<pid>-<random>`, which is removed when the
  update ends; one left by a program stopped part way through a download is
  removed by the next update.
- **Receipts show your machine's time again.** Update, crash and rollback
  receipts state their time in `daemon.timezone`, else the owner profile's
  zone, else the machine's own zone (3.4.0 and 3.4.1 wrote UTC). The zone is
  named after the time only when it is not the machine's. A refusal because
  another update or install holds the installation states its start time the
  same way.

## For client authors

- `update.status` and `update.check` answer with `installing`: the release
  being downloaded and installed now (`version`, `since`, `receivedBytes`,
  `file`), or null. `pendingVersion` is a release that was found and waits; it
  has not been downloaded yet.
- **Removed exports:** `DEFAULT_UPDATE_TIMEOUT_MS`; the `timeoutMs` option of
  the update functions and `updateTimeoutMs` of `DaemonAutoUpdaterOptions`;
  the `update-deferred` outcome of a launch update.
- **Changed exports:** `withUpdateBudget` is now `withUpdateCancellation` and
  ends only when the caller cancels; `UpdateRequestOptions` takes
  `onReceived(assetName, bytes)`, told of each piece of a release file as it
  arrives; `receiptTimeZone` returns undefined when no zone is set, and
  `formatReceiptTime` reads a missing zone as the machine's own.
