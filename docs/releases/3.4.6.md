# GoodVibes 3.4.6

GoodVibes 3.4.6 gives back the sign-in a browser on the daemon's own computer had
before 3.4.5, makes the web app work on a phone that opens it at the daemon's
plain-http network address, turns the web composer's model control into one
menu (provider, then model, then effort), keeps every program's model lists in
step with the providers, and names the permission chip for what it is. An
ordinary turn costs what it cost before.

## Upgrading

- **All programs must be on 3.4.6.** The daemon's model list answer
  (`models.list`) gained fields that a 3.4.5 program refuses to read, and the
  terminal apps' `/model refresh` asks the daemon's new `models.refresh`. The
  installer and the updater install them together.
- **Nothing stored changed.** 3.4.5 starts normally on a home 3.4.6 has
  started.

## Signing in a browser on the daemon's own computer

3.4.5 stopped printing a pairing code a phone could not open. On a daemon that
serves only its own computer (the default: bound to `127.0.0.1`), that left
`goodvibes pair`, `goodvibes-agent pair`, the terminal app's pairing screen and
the web app's "Pair a new device" with no code at all, and `goodvibes-daemon
pair` with a link but exit `1`. A browser on that same computer had nothing to
sign in with but the first-run password. Every one of them now gives a sign-in
for that browser again, said plainly as that, and draws no QR code (a QR code is
for another device):

```
This link signs in a browser on this computer. A phone cannot open it: the daemon serves only this machine: http://127.0.0.1:3421 is this machine's own address, which another device cannot open.
  1. done  The daemon serves the web UI at http://127.0.0.1:3421.
  2. next  goodvibes-daemon webui enable --lan
  3. then  goodvibes pair, then scan the code it prints with the phone.

  http://127.0.0.1:3421/#pair=<code>&offers=notifications%2Crelay%2Cpasskey
  Sign-in code: <code>  (to paste on the web UI's sign-in page, under Other ways to sign in)
```

- Open the link in a browser on that computer, or paste the code under "Other
  ways to sign in". `goodvibes pair`, `goodvibes-agent pair` and
  `goodvibes-daemon pair` exit `0`; `goodvibes-agent pair --json` and
  `goodvibes-daemon pair --json` say `"forThisMachine": true`.
- The daemon's start-up block says the same instead of drawing a QR code a
  phone could not open.
- The web app's Settings, Account, Devices and pairing shows "No pairing code
  for a phone: a phone could not open it yet (...)" with the steps, and below
  them "Make a sign-in link", which makes the link and the code for another
  browser on the computer running GoodVibes.
- When a phone can reach the daemon, everything is as in 3.4.5. A program
  connected to a daemon on another computer that serves only itself still gets
  the steps and no code: a link only that computer opens is no use there.
- The sign-in page now reads: "Run `goodvibes pair` on the computer running
  GoodVibes, then scan the code it shows, or open the link it prints in a
  browser on that computer." Its "Where do I find a code?" says what `pair`
  prints in each case.
- A daemon reached through Tailscale serve or another proxy without
  `web.publicBaseUrl` set: the daemon refuses a sign-in from that address
  (`403 ORIGIN_NOT_ALLOWED`, naming `web.publicBaseUrl`) in 3.4.4, 3.4.5 and
  3.4.6 alike, so no release gave such a page a working code; set
  `web.publicBaseUrl` to that address (the pairing screen's Tailscale serve does
  it for you).

## The web app on a phone over plain http

Opening the web app at the daemon's network address (`goodvibes-daemon webui
enable --lan`, then `http://192.168.x.x:3421`) showed "Something went wrong:
crypto.randomUUID is not a function" as soon as anything was pressed: browsers
give that function only to https and localhost pages. It now works there: chat,
sending, Work, Library, Personal and Settings were opened on such a page with
no page error. Copy buttons (a message, a code block, an artifact, a JSON
block, "Sign in again") copy another way where the browser keeps the
clipboard from the page; when the browser refuses that too, they select the
text and say "Selected: press Ctrl+C (Cmd+C on a Mac) to copy it." Install,
push notifications, the microphone and the camera scanner still need https and
say so, as before.

## Choosing a model in the web app

The model control under the message box is one menu: click it and pick the
provider, then the model, then the effort, without going to Settings.

- **Step 1, provider.** Providers you are connected to come first, each with
  its model count; the others follow under "Not connected" with the one action
  that connects them: "Connect in Settings", or "Copy /provider sign-in <id>"
  where only the terminal app can sign in.
- **Step 2, model.** Favorites (pinned models), Recent, then the rest, and last,
  under "Not described by the catalog", the models marked "kind unknown": the
  terminal model picker's order and words. Image, speech and embedding models
  are not listed.
- **Step 3, effort,** only for a model that has effort levels, with the one in
  use checked. The model and its effort are applied together.
- A filter box at the top searches every connected provider's models at once.
  Arrows move, Right or Enter goes into the next step, Left or Escape goes back
  one step. On a phone the same steps open in a bottom sheet.
- The control reads the model and the effort ("Alpha Chat 1 Medium"); the
  separate effort list that sat under the models is gone (one place for the
  choice).
- A pick is for this chat only, as in 3.4.5, and the menu says so: "For this
  chat only. The default for new chats is set in Settings." Beside it, "Make
  this the default for new chats" saves the chat's model and effort as the
  default from the menu.

## Model lists that go stale

Why some providers' models were "not refreshed, very stale", by kind of
provider:

- **A provider listed from the model catalog** (one with no model listing of its
  own): the daemon checked the catalog only when it started. A daemon running
  as a service for weeks kept the catalog it started with. It now checks the
  catalog again, at the moments it already re-reads lists (a model list being
  read, the model menu or picker opening), once its last check is a day old.
- **A built-in provider with a listing** (OpenAI, Anthropic, Gemini, OpenRouter,
  Foundry and the like): its list is kept on disk for a day, and a read within
  that day answers from disk. That rule stands. But the read that found a list
  due answered with the old list, and the new one, read in the background,
  was announced to no one: the web app kept showing the old list. A list that
  changes is now announced, and every program reads the one list again.
- **The web app** did not read the model list again when the daemon announced a
  provider change; it does now.
- **The terminal app and the Agent:** `/model refresh` read only that program's
  own lists, not the daemon's (the lists the web app shows); it now asks the
  daemon too and says "The daemon read its lists again too (what the web UI and
  the other programs show): 5 providers answered". In the model picker,
  `Ctrl+R` ran a command that does not exist (`Unknown command:
  /refresh-models`); it now runs `/model refresh`.
- **A custom provider** (a file in `providers/`) has no list on disk and is read
  every time; it was never stale.

The model menu says when a provider's list was read when it is more than a day
old ("List read 3 days ago") and when its last reading failed ("Could not read
its list now"). "Refresh models" reads the lists again from the providers (one
provider in its step, every provider in the first step) and says what it found,
for example "Microsoft Foundry: 2 models found (1 new, 1 retired)." For
programs: `models.refresh` (`POST /api/models/refresh`, optional `providerId`; an admin's,
since it sends requests to the providers with the owner's credentials),
and `models.list` now carries `modelList` (`source`, `listedAt`, `error`) for each
provider, `textWork` for each model, and `pinned` and `recent`.

## Permissions

The status bar of both terminal programs and the web app's header chip say
`Permissions:` where they said `Asks:`: `Permissions: Jev decides`,
`Permissions: Ask me`, `Permissions: YOLO`. While the mode in force is not the
one chosen, they read `Permissions: asking you, for now · Jev decides once a
decision model is set` (it was `Asks: you, for now · ...`), or `Permissions:
YOLO, for now · Ask me once the old auto-approve setting is off`. The setting is
still named "When GoodVibes asks"; no setting or command was renamed. On a phone
the chip reads `Permissions: asking you, for now`, whole; the header's gaps are
a little tighter so its buttons stay on screen.
