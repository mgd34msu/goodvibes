# Saved-data compatibility and native updates

Installed GoodVibes programs publish reader requirements before writing a format that older builds cannot safely read. The TUI, Agent and daemon share `.goodvibes-reader-requirements.json` beside their executables. It contains format names and the minimum supported version, without configuration values or saved content.

This applies to knowledge schemas 12 through the current one, configuration policy epochs version 2 (written by earlier builds; the settings revision that replaced them is a new file older readers never open), contract review observations, native conversation captures that record settlement (these need version 3.3.0 or newer; the other formats need 3.1.2 or newer), and the daemon's newer payment, inbox and device formats. A program publishes every format it can write in one step, at its first data write after it starts; each later write checks a list in memory and touches no file. Opening an empty knowledge store, reading configuration, and help, metadata or recovery commands publish nothing. Because the formats go out together, the requirement becomes 3.3.0 as soon as a 3.3.0 or newer program writes any data. If an installed peer cannot confirm one of the formats, the program falls back to publishing each format as it first writes it, so only a write of a format the peer cannot read is held.

Before introducing an additional format, the installed publisher also checks every present TUI, Agent and daemon in its installation directory. Their reader profiles must confirm the same suite version and all required formats, bound to their actual installed program bytes. Missing or incompatible peer evidence holds the new publication until the suite is updated. Unchanged evidence is checked through physical revisions; ordinary writes do not repeatedly hash programs.

The release installer checks every selected program before replacing the first installed program. Terminal self-update and rollback check the candidate under their existing file transaction claims. New terminal releases include checksum-verified `*.reader-ci-artifact.json` metadata, installed as `<executable>.readers.json`; the executable and its reader metadata are kept and restored together. That metadata binds the reader capabilities to the actual executable and any captured Bun companions. A version label alone is insufficient.

macOS daemon releases also include reader metadata beside the daemon and its required `lib/sqlite-darwin-<architecture>/libsqlite3.dylib` and producer record. The installer downloads these released companions and preserves their expected paths and permissions. No local SQLite compilation is part of installation.

When saved data requires a format that the proposed build cannot confirm, installation or rollback stops and keeps the current files. Historical terminal binaries without reader metadata are also refused when a saved-data requirement exists. GoodVibes does not start an older program to guess whether it understands the new data. Keep the current installation and choose a release with matching reader support. Deleting the requirement file does not convert saved data to an older schema.

The native publisher is admitted by the compiled executable root before its first awaited startup work. Linux also checks the OS-loaded executable inode; Darwin retains the initially selected physical executable and rejects later replacement. This publisher only records compatibility restrictions. It grants no permission to read private data or execute saved work. Source and package-managed runs retain their existing explicit store behavior and do not infer an installed publisher from a filename or environment variable.

Contract checkpoints live under `.goodvibes/contracts/checkpoints-v7/<id>/` (earlier builds wrote one file per contract under `checkpoints-v6/`, which is read and moved into the directory on the contract's first save); older running programs do not scan or quarantine either. Older checkpoint files remain readable through explicit compatibility lookup. Durable admission identities and execution leases retain their original locations, so restart or migration cannot mint a second execution of the same admitted operation. Updating programs does not kill other terminal sessions.
